# 分组动态倍率与 OpenAI 上游调度设计

## 状态

设计已于 2026-07-30 在对话中确认，等待书面复核。

## 摘要

在现有分组管理中增加手动开启的“动态倍率”。开启后，该分组的 OpenAI Token 请求优先选择上游实际倍率低且首 Token 表现合格的已验证中转账号，并按最终选中账号的上游倍率计算用户实际倍率：

```text
倍率上限 = 用户分组专属倍率（若有），否则为分组倍率
基础倍率 = min(上游实际倍率 × 2, 倍率上限)
最终倍率 = 基础倍率 × 本地分组当前高峰因子
```

设计复用现有上游倍率探测、OpenAI 账号筛选、并发控制、限流、会话粘性和失败重试能力，不新建第二套探测或转发框架。

## 目标

- 让管理员可在任意现有分组中手动开启动态倍率。
- 只影响该分组内的 OpenAI Token 计费请求。
- 复用现有 `/v1/sub2api/billing` 探测结果识别兼容上游中转并获得实际倍率。
- 在可用的已验证中转中优先使用低倍率账号。
- 对流式请求，使用近期 P90/P50 避开首 Token 持续偏慢的低倍率账号。
- 所有账号的首 Token 都不合格时，回退到低倍率优先，不因性能数据拒绝服务。
- 让调度、限额、余额或订阅额度扣减、成本计算和用量日志使用同一份不可变倍率快照。
- 开关默认关闭，保证升级后现有分组行为不变。

## 非目标

- 不替换或重写现有上游倍率探测服务。
- 不改变现有全局“低倍率优先”和“OpenAI 实验调度策略”对未开启动态倍率分组的行为。
- 不将探测倍率覆盖到账号手工倍率或分组倍率字段。
- 不通过账号名、JSON 文件名、Base URL 域名或其他启发式规则猜测是否为中转。
- 不对 OAuth 或 OpenAI 官方直连账号套用动态倍率公式。
- 不对图片、视频、网页搜索等按次计费改用动态倍率。
- 不按模型分开统计首 Token；本期按账号统一统计。
- 不在用户请求链路上同步调用倍率探测接口或扫描历史用量表。

## 现有能力

项目已经具备以下能力，实现应直接复用：

- OpenAI API Key 账号可调用兼容 Sub2API 上游的 `/v1/sub2api/billing`。
- 现有探测快照包含探测状态、收到时间、有效期、下次探测时间和完整计费数据。
- 全局探测默认周期为 30 分钟，并已有全局开关、账号开关、单账号手动探测和批量探测接口。
- 现有 OpenAI 调度器已处理账号状态、模型能力、并发槽位、限流、会话粘性和失败切换。
- 用量日志已保存流式标记、账号、首 Token 耗时和最终用户计费倍率。
- 现有 OpenAI 调度也有账号级 TTFT EWMA，但本功能不用 EWMA 代替新确认的 10 条样本 P90/P50 规则。

## 术语和渠道判定

### 已验证上游中转

一个账号只有同时满足以下条件才参与动态倍率排序：

1. `platform=openai`。
2. `type=api_key`。
3. 现有探测逻辑能从快照解析出当前有效的上游 Token 倍率。
4. 探测协议已验证 `object=sub2api.key_billing`、`schema_version=1`、`billing_scope=token` 及合法数值字段。

实现应以现有 `openAIFreshUpstreamBillingRate` 或等价的单一解析入口为权威判定，避免调度和计费各自解析一次而产生差异。

### 非中转或未验证账号

以下账号不参与动态倍率和 P90/P50 排序，但保留为最终可用性兜底：

- OpenAI OAuth 账号，包括通过 RT JSON 导入的官方账号。
- OpenAI 官方 API Key 直连账号。
- 不支持标准 Sub2API 计费接口的中转。
- 没有有效探测快照或快照已过期的 API Key 账号。

RT JSON 导入流程已将账号创建为 `OpenAI + OAuth`，因此不会被误判为可动态计费的 API Key 中转。对于探测失败的 API Key，系统不需要断言它一定是官方渠道；只需将它安全地归为“不参与动态倍率，仅兜底”。

## 分组配置和数据模型

在分组上增加：

- `dynamic_rate_enabled BOOLEAN NOT NULL DEFAULT FALSE`。
- `dynamic_rate_ttft_threshold_ms INTEGER NOT NULL DEFAULT 5000`。

阈值规则：

- 界面以秒为单位显示，后端以毫秒存储和比较。
- 可配置范围为 1-60 秒，默认 5 秒，步进 1 秒。
- 关闭动态倍率时保留阈值，再次开启时继续使用。
- 新建、编辑、详情、列表、复制分组及缓存快照必须完整携带两个字段。

管理界面文案：

```text
动态倍率
仅适用于上游中转渠道
首 Token 阈值（秒）
```

只在打开动态倍率时显示阈值输入。

## 复用现有倍率探测

本功能不增加新的探测线程、周期、协议、数据格式或全局设置。继续使用现有：

- `UpstreamBillingProbeService`。
- 全局自动探测开关和 30 分钟默认周期。
- 账号级 `upstream_billing_probe_enabled`。
- 单账号及批量手动探测能力。
- `accounts.extra.upstream_billing_probe` 中的现有快照、有效期和失败保留规则。

开启动态倍率或将 API Key 账号加入已开启的分组时，可直接调用现有的账号探测开启和批量探测能力进行一次初始刷新，但不复制其实现。这是管理操作后的异步最佳努力任务：初始探测失败不回滚分组开关，该账号先作为未验证兜底账号。

关闭某个分组的动态倍率时，不自动关闭账号级探测，因为同一账号可能还被其他分组使用。

## 首 Token 样本

### 样本口径

每个 OpenAI 账号维护一个统一窗口，不区分模型。样本必须同时满足：

- 请求是流式请求。
- 上游请求成功。
- `first_token_ms > 0`。
- 不是客户端主动取消。
- 能明确关联到实际承接的账号。

窗口规则：

- 只保留最近 24 小时内最新 10 条有效样本。
- 超过 24 小时的样本失效。
- 新样本加入后，超过 10 条时淘汰最旧样本。
- 有效样本达到 10 条后才认为统计成熟。

百分位使用确定性 nearest-rank 规则：将 10 条数据按耗时从小到大排序，P50 取第 5 条，P90 取第 9 条。因此单次尾部抖动不会立即将 P90 推高，但最近 10 次中出现至少约 2 次慢请求时会反映到 P90。

### 预热和持续更新

- 开启动态倍率、服务启动或样本缓存丢失时，在后台从用量日志为相关账号加载最近 24 小时内最新 10 条有效样本。
- 这个历史查询不得在每个用户请求中执行。
- 后续每个流式请求结束后，异步将新样本写入滚动窗口，不阻塞当前响应。
- 样本以 Redis 作为多实例共享存储；Redis 不可用时允许使用进程内缓存，但禁用探索路由并回退到低倍率优先，避免多实例重复探索。

### 探索流量

样本不足 10 条的账号为“待观察”。为避免第二、第三低倍率账号长期没有数据：

- 只使用无粘性的新流式会话探索。
- 探索流量不超过该分组合格流式请求的 5%。
- 待观察账号之间轮转获得探索机会。
- 单个待观察账号最多同时承接 1 个探索请求。
- 任一探索请求出现可重试错误或首 Token 超过当前分组阈值，立即停止该账号探索 5 分钟，不必等满 10 个差样本。
- 已成熟且 P90 超过阈值的账号不获得探索流量；它通过之后的兜底或正常请求样本自然恢复。

5% 是上限，不是强制比例。没有待观察账号、存在会话粘性、探索并发已占用或共享缓存不可用时，不发生探索。

## 调度策略

### 通用前置规则

以下现有规则始终优先：

1. 必要的 `previous_response_id` 和 `session_hash` 会话粘性。
2. 账号活动、可调度、未过期、未冷却。
3. 请求模型、传输方式、端点和能力匹配。
4. 限流、配额自动暂停、并发槽位和排队约束。
5. 重试过程中已失败的账号排除集。

如果粘性账号仍然合法可用，继续使用它，即使它不是最低倍率。最终计费按实际选中账号处理。

### 非流式请求

非流式请求不判断首 Token，只要账号未被现有异常、限流、冷却、并发和能力规则排除，就可以使用。在所有合格的已验证中转中：

1. 上游实际倍率低者优先。
2. 倍率相同时选择当前负载和队列更优者。
3. 动态倍率模式下不使用账号手工优先级。

如果最低倍率账号的实际转发返回现有重试分类认定的可重试异常，本次请求排除该账号，沿用现有冷却/限流状态，然后选择第二低倍率账号。客户端参数错误等不可重试错误不得通过换账号重试。

### 流式请求

除了少量受控探索请求，正常流式选择使用以下规则：

1. 从合格的已验证中转中找到样本成熟且 `P90 <= 分组首 Token 阈值` 的账号。
2. 如果存在合格账号，选择上游实际倍率最低者。
3. 倍率相同时，依次比较 P90、P50、当前负载和队列。
4. 如果没有任何成熟且 P90 合格的账号，不拒绝请求，回退到全部合格中转中的最低倍率账号。

该规则等价于“先看低倍率，低倍率账号首 Token 不合格时换第二低倍率，全部不合格时仍低倍率优先”。

首 Token 判断只使用历史数据，影响后续请求。调度器不会在当前请求中先等待阈值再换账号，也不会在已向客户端输出内容后重放请求。

### 中转全部不可用

所有已验证中转都被现有账号规则排除时，允许使用 OAuth、官方直连或未验证账号作为最终兜底。兜底选择继续使用现有调度和故障切换规则，不使用上游动态倍率和 P90/P50。

## 计费规则

### 上游实际倍率

对已验证中转，使用账号选中时现有探测快照解析出的当前有效倍率。该倍率是上游返回的 `effective_rate_multiplier` 语义，包含上游自身的用户专属倍率和当前高峰规则。现有探测快照携带高峰时间表时，可继续使用现有逻辑按当前时间重算。

不使用本地 `accounts.rate_multiplier`。该字段仍用于原有账号统计成本口径。

### 用户倍率公式

对最终选中已验证中转的 OpenAI Token 计费请求：

```text
cap = user_group_rate_override ?? group.rate_multiplier
base = min(upstream_effective_rate_multiplier * 2, cap)
final = base * group.PeakMultiplierAt(captured_at)
```

示例：

```text
上游倍率 0.03，上限 0.08 -> 基础倍率 0.06
上游倍率 0.05，上限 0.08 -> 基础倍率 0.08
基础倍率 0.08，本地高峰因子 1.5 -> 最终倍率 0.12
```

本地高峰因子仍只按现有订阅分组规则生效，并在动态基础倍率之后相乘。

如果最终使用的是 OAuth、官方直连或未验证账号，则不进入动态公式：

```text
base = cap
final = base * group.PeakMultiplierAt(captured_at)
```

### 计费范围

动态公式仅替换 OpenAI Token 计费路径的基础倍率。

- Chat、Responses、Completions、Embeddings 等 Token 计费使用动态倍率。
- 图片渠道如果明确使用 Token 计费，继续属于 Token 路径。
- 图片、视频按次计费继续使用现有独立价格和倍率。
- 网页搜索按次计费继续使用现有基础倍率口径。
- 标准余额分组和订阅分组都可开启动态倍率。

## 不可变计费快照

账号选中后立即生成请求级快照，至少包含：

- 是否开启动态倍率。
- 最终选中账号和渠道分类。
- 倍率来源：已验证探测或上限兜底。
- 上游实际倍率（若适用）。
- 探测收到时间和有效期（若适用）。
- 分组倍率、用户专属倍率和最终上限。
- 基础倍率、本地高峰因子和最终倍率。
- 快照时间 `captured_at`。

该快照必须作为显式参数进入：

- 请求限额和配额检查。
- 余额扣减。
- 订阅额度消耗。
- `CostBreakdown.ActualCost` 计算。
- 用量日志。

异步计费任务不得重新查询当前分组倍率、当前探测倍率或当前高峰时段。这保证请求执行期间配置变化不会造成“按一个倍率选择，按另一个倍率扣费”。

发生可重试失败并切换账号时，旧快照作废，为最终实际承接请求的账号重新生成快照。一旦已将流式内容发送给客户端，不为调度优化重放请求。

## 用量日志和审计

`usage_logs.rate_multiplier` 继续存储用户最终实际倍率。`usage_logs.account_rate_multiplier` 继续保留现有账号统计口径，不改成上游探测倍率。

为避免为未来快照字段反复添加列，在用量日志增加一个可空、版本化的 JSONB 计费上下文，例如 `dynamic_rate_context`。只有开启动态倍率的请求写入，内容对应上述不可变快照。

普通用户 DTO 不得返回账号身份、上游倍率、探测时间和内部倍率计算过程。管理员 DTO 可返回完整上下文用于账单解释和问题排查。

## 用户和管理界面

### 分组管理

- 在现有分组新建/编辑表单显示“动态倍率”开关。
- 开关下方显示备注“仅适用于上游中转渠道”。
- 开启时显示“首 Token 阈值”数字输入，后缀为“秒”。
- 复制分组时复制开关和阈值。
- 开启动态倍率的分组不删除账号手工优先级，只在该分组的请求中忽略它。

### 管理员账号和用量视图

管理员可看到：

- 渠道判定：已验证中转、OAuth/官方账号、未验证或不兼容。
- 上游实际倍率、探测状态、收到时间和有效期。
- 账号最近 24 小时有效首 Token 样本数、P50 和 P90。
- 管理员使用记录列表和详情显示该请求实际采用的“上游中转倍率”；使用 OAuth、官方直连或未验证账号兜底时显示“未使用中转”。该字段仅由管理员 DTO 返回。
- 用量详情中的动态计费快照和最终选择原因。

### 普通用户

- 分组、套餐和密钥页面显示“动态倍率，最高 ×X”，其中 X 是该用户当前适用的分组倍率上限。
- 用量明细继续显示每次请求的实际最终倍率。
- 不显示上游账号、上游成本倍率、P50/P90 或内部调度原因。

## 与现有调度开关的关系

- 分组未开启动态倍率时，完全沿用现有全局“低倍率优先”或“OpenAI 实验调度策略”及固定分组倍率计费。
- 分组开启动态倍率时，本设计的确定性分组策略优先，不让全局加权分数将高倍率账号排在合格的低倍率账号前。
- 本策略仍复用现有会话粘性、并发、负载、队列、限流、能力匹配和故障切换。
- 现有全局开关、账号优先级和权重配置不删除。

## 故障处理和降级

- 倍率探测失败：不阻塞分组保存或用户请求；账号降为未验证兜底。
- 历史样本预热失败：账号作为待观察，但不在请求链路同步查库。
- Redis 不可用：禁用 5% 探索，可使用进程内样本做最佳努力排序；数据不足时直接低倍率优先。
- 调度样本数据异常：忽略非法耗时并保留最近合法窗口。
- 可重试上游失败：延用现有错误分类、排除集和冷却逻辑，按调度顺序选下一账号。
- 所有已验证中转不可用：使用非中转/未验证账号兜底，并按用户/分组上限计费。
- 用户专属倍率查询失败：沿用现有缓存和安全回退规则，不使用上游倍率扩大用户价格上限。
- 计费快照缺失：对动态倍率请求按上限计费并记录结构化告警，不可默认为 1 倍或 0 倍。

## 性能约束

- 用户请求不同步调用上游倍率接口。
- 用户请求不同步扫描用量日志。
- 探测倍率、P50/P90 和探索状态均从调度快照或缓存读取。
- 流式请求结束后的样本更新异步执行。
- 动态倍率带来的新增调度耗时目标为 P95 小于 5 毫秒。

5% 探索可能让极少量请求进入尚未验证速度的账号，这是获得第二、第三账号真实首 Token 数据的必要成本。历史日志预热、无粘性限制、单账号探索并发 1 和首次差样本立即冷却用于限制用户体验风险。

## 测试策略

### 分组和 API

- 新建分组默认关闭动态倍率，阈值默认 5000 毫秒。
- 创建、编辑、详情、列表和复制正确保存两个字段。
- 拒绝小于 1 秒、大于 60 秒、非整数或非有限数的阈值。
- 分组缓存、API Key 上下文和调度快照能在配置更新后及时失效。

### 渠道判定和探测复用

- RT JSON 导入账号被识别为 OAuth 并排除于动态排序。
- 具有新鲜合法 Sub2API 快照的 API Key 被识别为已验证中转。
- 官方 API Key、不兼容中转、探测失败和过期快照只作为兜底。
- 动态倍率复用现有有效期和上游高峰重算规则。
- 开启分组时的初始探测调用现有服务，不创建第二个周期任务。

### 调度

- 非流式请求选择最低倍率的无异常可用账号。
- 最低倍率账号返回可重试异常时切换到第二低倍率账号。
- 不可重试的客户端错误不切换账号。
- 流式请求在最低倍率账号 P90 合格时使用该账号。
- 最低倍率账号 P90 超标时选择下一个倍率低且 P90 合格的账号。
- 全部成熟账号 P90 超标时回退到最低倍率。
- 倍率相同时按 P90、P50、负载和队列破平。
- 粘性账号可用时保持粘性，不为低倍率破坏会话。
- 中转全部不可用时能够使用 OAuth/官方/未验证账号兜底。
- 动态分组忽略手工账号优先级，关闭动态倍率后恢复原行为。

### 样本和探索

- 历史预热只取每账号最近 24 小时内最新 10 条有效流式记录。
- 非流式、失败、无 `first_token_ms` 和客户端取消记录不进入窗口。
- P50/P90 的 nearest-rank 计算正确且稳定。
- 新样本异步追加，第 11 条淘汰最旧样本。
- 过期样本被淘汰后，账号恢复为待观察。
- 探索总量不超过 5%，只选择无粘性新流式会话，每账号探索并发不超过 1。
- 首个探索错误或超阈值样本立即触发 5 分钟探索冷却。
- Redis 异常时不重复探索且不阻塞请求。

### 计费

- 无用户专属倍率时使用分组倍率作为上限。
- 有用户专属倍率时使用其作为上限。
- 上游倍率乘 2 低于上限时使用动态结果。
- 上游倍率乘 2 高于上限时按上限计费。
- 本地高峰因子在动态基础倍率之后相乘。
- OAuth/官方/未验证兜底按用户/分组上限计费。
- Token 计费使用动态倍率，图片/视频/搜索按次计费不受影响。
- 余额、订阅额度、限额、成本和日志使用同一快照。
- 请求期间上游倍率或分组配置变化不改变已捕获的请求快照。

### 前端

- 分组新建、编辑和复制正确展示动态倍率开关和阈值。
- 阈值的默认值、范围、步进和秒/毫秒转换正确。
- 备注精确显示“仅适用于上游中转渠道”。
- 用户侧只显示最高倍率和实际请求倍率，用量 API 和页面均不返回上游中转倍率。
- 管理员使用记录列表和详情可见上游中转倍率，并可查看渠道判定、P50/P90、样本数和计费上下文。

### 完整验证

- 后端 Go 单元测试和相关集成测试。
- 前端单元测试、TypeScript 类型检查、ESLint 和生产构建。
- 分组和用量日志数据库迁移在空库和现有数据库上验证。
- 浏览器验证分组表单的桌面和移动端布局，包括长分组名、阈值错误和开关切换。
- 性能测试确认无请求级上游探测或用量扫描，新增调度耗时 P95 小于 5 毫秒。

## 部署和回滚

部署步骤：

1. 执行分组新字段和用量计费上下文迁移。
2. 同时部署后端和前端。
3. 保持所有现有分组的动态倍率关闭。
4. 先对一个含少量已验证中转的分组开启，核对调度决策、用量快照、余额/订阅额度和实际上游费用。
5. 监控探测有效率、中转兜底率、探索比例、P90 超标率、账号切换率和计费快照缺失告警后再扩大开启范围。

回滚时关闭分组动态倍率即可恢复原调度和固定倍率计费。新字段和历史 `dynamic_rate_context` 保留，旧版本不读取它们；不在回滚过程中删除审计数据。
