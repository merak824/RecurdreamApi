# OpenAI 全局首 Token 优化与分组动态倍率调度设计

## 状态

动态倍率设计已于 2026-07-30 完成书面复核；全局首 Token 优化设计已于 2026-07-31 在对话中确认并合并修订。核心实现已落地，当前进入集成验证和发布前检查。

### 当前实现状态

- 已完成真实语义首 Token 识别、HTTP SSE/Responses WebSocket 口径接入、24 小时窗口与每账号+传输最新 10 条样本、管理员诊断上下文，以及流式请求结束后的异步样本更新。
- 已完成同一手工优先级层内的成熟 P90/P50 排序、稳定哈希灰度、无粘性探索候选、Redis 租约与 5 分钟冷却；非流式请求不参与首 Token 排序或探索。
- 调度选择会在 3 毫秒预算内批量读取 Redis 共享窗口；Redis 成功时使用跨实例快照，Redis 超时或异常时回退进程内窗口并停用探索，不阻塞用户请求。
- 当前探索比例由 Redis 按分组、手工优先级层和上游传输原子累计，严格不超过配置值；Redis 租约继续负责单账号并发、令牌所有权和冷却。
- 尚需在联网环境重跑 `go generate ./ent`，并完成后端 race、完整服务测试和 HTTP SSE/透传集成验证；这些验证未完成前不应扩大灰度。

## 摘要

本设计包含两个层次，必须由同一套 OpenAI 调度和转发链路实现，不能复制成互相竞争的调度器：

1. **全局首 Token 优化**是系统底层优化项，不是分组功能，也不增加管理员业务开关。所有 OpenAI 文本流式请求统一使用真实语义首 Token 计时、P90/P50 稳定性排序、受控探索、HTTP/2/Responses WebSocket 连接复用和安全的首输出长尾切换。非流式请求只复用连接，不参与首 Token 排序或超时切换。
2. **分组动态倍率**是管理员手动开启的可选计费和排序策略。开启后，该分组的 OpenAI Token 请求在复用全局首 Token 样本和传输优化的基础上，优先选择上游实际倍率低且首 Token 表现合格的已验证中转账号，并按最终选中账号的上游倍率计算用户实际倍率：

```text
基础倍率上限 = 用户分组专属倍率（若有），否则为分组倍率
基础倍率 = min(上游实际倍率 × 2, 基础倍率上限)
最终倍率 = 基础倍率 × 本地分组当前高峰因子
```

这里的“上限”只限制基础倍率。本地订阅分组启用高峰倍率后，最终倍率允许高于基础倍率上限；所有用户界面必须同时展示基础倍率上限和可能额外生效的高峰因子，不得将基础倍率上限简称为无条件的“最高倍率”。

设计复用现有上游倍率探测、OpenAI 账号筛选、并发控制、限流、会话粘性、HTTP/2 客户端池、Responses WebSocket 连接池、首输出保护和失败重试能力，不新建第二套探测、样本或转发框架。

## 目标

- 将 OpenAI 文本流式请求的首 Token 优化为全局系统能力，与动态倍率开关解耦。
- 使用统一且不可伪造的语义首 Token 口径，排除响应头、`response.created`、心跳、元数据、usage-only 和终止事件。
- 在不越过普通分组手工账号优先级的前提下，优先使用近期 P90/P50 更快、更稳定的账号。
- 复用 HTTP/2 和 Responses WebSocket 连接池，减少 DNS、TCP、TLS 和重复建连带来的首 Token 开销。
- 对极端无输出长尾最多串行切换一次账号，禁止并发双发，并保护强粘性、会话状态和计费安全。
- 让管理员可在任意现有分组中手动开启动态倍率。
- 动态倍率只影响该分组内的 OpenAI Token 计费和低倍率排序；关闭动态倍率不关闭全局首 Token 优化。
- 复用现有 `/v1/sub2api/billing` 探测结果识别兼容上游中转并获得实际倍率。
- 在可用的已验证中转中优先使用低倍率账号。
- 对流式请求，使用近期 P90/P50 避开首 Token 持续偏慢的低倍率账号。
- 所有账号的首 Token 都不合格时，回退到低倍率优先，不因性能数据拒绝服务。
- 让调度、限额、余额或订阅额度扣减、成本计算和用量日志使用同一份不可变倍率快照。
- 让参与公式的倍率使用统一十进制定点精度，保证扣费、用量日志和审计上下文可严格对账。
- 开关默认关闭，保证升级后现有分组行为不变。

## 非目标

- 不把首 Token 优化做成新的分组开关、套餐功能或用户可选功能；仅保留内部灰度和紧急回滚配置。
- 不并发向多个账号发送同一个请求，不实现 hedging/racing，也不以增加常态重复上游费用换取速度。
- 不通过修改模型、推理等级、提示词、工具、`store` 或其他请求语义伪造首 Token 优化。
- 不把网关心跳或上游非语义前导事件展示成模型首 Token。
- 不替换或重写现有上游倍率探测服务。
- 普通分组不越过账号手工优先级；只在同一最高优先级层内增加确定性的 P90/P50 排序。
- 不将探测倍率覆盖到账号手工倍率或分组倍率字段。
- 不通过账号名、JSON 文件名、Base URL 域名或其他启发式规则猜测是否为中转。
- 不对 OAuth 或 OpenAI 官方直连账号套用动态倍率公式。
- 不对图片、视频、网页搜索等按次计费改用动态倍率。
- 不改变 OpenAI Live/Realtime；图片、视频、搜索按次及 Live/Realtime 不进入文本首 Token 样本、探索或首输出切换。
- 不按模型分开统计首 Token；本期按“账号 + 实际上游传输”统计。
- 不在用户请求链路上同步调用倍率探测接口或扫描历史用量表。

## 全局首 Token 优化

### 适用范围

全局首 Token 优化覆盖 OpenAI 平台下产生文本语义流的 Chat Completions、Completions、Responses SSE、Responses WebSocket、`/responses/compact` 流式桥接，以及分发到 OpenAI 账号的 Messages 流式请求。账号可以是已验证中转、未验证 API Key、官方 API Key 或 OAuth；渠道分类不影响全局首 Token 样本资格。

非流式请求继续受益于 HTTP/2、客户端缓存和连接复用，但不读取 P90/P50、不产生首 Token 样本、不参与探索，也不执行首输出超时切换。图片、视频、网页搜索按次、模型列表、token 计数和 Live/Realtime 明确排除。

### 延迟分层

必须同时区分以下指标，不能只保留一个无法解释的总耗时：

- 用户感知 TTFT：从请求进入网关到首个可展示语义内容写给客户端。
- 路由耗时：请求解析、资格过滤和账号排序耗时。
- 排队耗时：等待账号并发槽位或连接容量的耗时。
- 连接获取耗时：从开始获取上游传输到取得可写 HTTP/WS 连接的耗时，并标记冷连接或热连接。
- 上游 TTFT：从本轮请求真正写给上游到收到首个可展示文本、Token 或工具参数 delta；只有该指标进入账号 P50/P90 窗口。

现有 `usage_logs.first_token_ms` 的对外语义和历史接口不得静默改变。本期明确新增可空的 `usage_logs.upstream_first_token_ms INTEGER` 作为调度样本值，并新增 `usage_logs.client_disconnected BOOLEAN NOT NULL DEFAULT FALSE`；现有 `request_type`/`openai_ws_mode` 用于还原 `http_sse` 或 `responses_ws`。所有 HTTP、WebSocket ingress、WebSocket passthrough 和桥接路径必须写入同一口径。旧记录缺少上游 TTFT、传输类型、客户端取消标记或明确起点时，不得直接作为成熟样本。

### 系统参数

首 Token 优化不增加管理端业务开关。以下参数属于部署配置或内部灰度/紧急回滚能力：

- `gateway.openai_ttft_optimizer_enabled`：内部发布门，最终目标为默认开启；关闭时恢复现有调度但继续记录指标。
- `gateway.openai_ttft_optimizer_rollout_percent`：按稳定请求哈希灰度全局 P90/P50 排序，范围 `0-100`，不允许各实例独立随机决定。
- `gateway.openai_ttft_stable_threshold_ms`：普通分组的全局稳定门槛，默认 `5000` 毫秒。
- `gateway.openai_ttft_exploration_percent`：探索上限，范围 `0-5`，上线时按 `0 -> 1 -> 5` 调整；多实例由 Redis 原子累计配额执行精确上限。
- `gateway.openai_first_output_timeout_seconds`：普通推理首输出长尾阈值，安全灰度后的目标默认值为 `30` 秒；显式配置 `0` 可紧急关闭。
- `gateway.openai_high_effort_first_output_timeout_seconds`：`high/xhigh/max` 的阈值，目标默认值为 `120` 秒。

配置必须在启动时严格校验：发布比例为 `0-100`、探索比例为 `0-5`、稳定门槛为 `1000-60000` 毫秒；普通首输出超时沿用 `0` 或 `30-600` 秒，高推理超时沿用 `0` 或 `30-1800` 秒。非法值必须阻止启动或拒绝配置更新，不能静默截断。

动态倍率分组继续使用自己的 `dynamic_rate_ttft_threshold_ms` 覆盖全局稳定门槛，但不能覆盖 30/120 秒的当前请求首输出长尾阈值。5 秒稳定门槛只影响后续请求选哪个账号，绝不表示当前请求等待 5 秒就重试。

## 术语和渠道判定

### 已验证上游中转

一个账号只有同时满足以下条件才参与动态倍率排序：

1. `platform=openai`。
2. `type=api_key`。
3. 现有探测逻辑能从快照解析出当前有效的上游 Token 倍率。
4. 探测协议已验证 `object=sub2api.key_billing`、`schema_version=1`、`billing_scope=token` 及合法数值字段。
5. 当前重算得到的上游倍率严格大于 0。零倍率虽然可由现有探测协议解析，但动态倍率默认不接受，以免错误或恶意快照将用户计费降为免费；如未来需要支持免费渠道，必须增加独立的管理员显式授权，不能复用本开关隐式放行。

实现应以现有 `openAIFreshUpstreamBillingRate` 或等价的单一解析入口为权威判定，避免调度和计费各自解析一次而产生差异。

### 非中转或未验证账号

以下账号不参与动态倍率的低倍率/P90 门槛排序，但保留为最终可用性兜底；它们仍参与普通分组的全局首 Token 采样和同优先级 P90/P50 排序：

- OpenAI OAuth 账号，包括通过 RT JSON 导入的官方账号。
- OpenAI 官方 API Key 直连账号。
- 不支持标准 Sub2API 计费接口的中转。
- 没有有效探测快照或快照已过期的 API Key 账号。

RT JSON 导入流程已将账号创建为 `OpenAI + OAuth`，因此不会被误判为可动态计费的 API Key 中转。对于探测失败且没有可沿用新鲜成功快照的 API Key，系统不需要断言它一定是官方渠道；只需将它安全地归为“不参与动态倍率，仅兜底”。管理员界面对此类账号显示“倍率未验证”，不得显示“未使用中转”。

## 分组配置和数据模型

在分组上增加：

- `dynamic_rate_enabled BOOLEAN NOT NULL DEFAULT FALSE`。
- `dynamic_rate_ttft_threshold_ms INTEGER NOT NULL DEFAULT 5000`。

阈值规则：

- 界面以秒为单位显示，后端以毫秒存储和比较。
- 可配置范围为 1-60 秒，默认 5 秒，步进 1 秒。
- 关闭动态倍率时保留阈值，再次开启时继续使用。
- 新建、编辑、详情、列表、复制分组及缓存快照必须完整携带两个字段。

管理界面文案：

```text
动态倍率
仅适用于上游中转渠道
基础倍率最高 ×X，高峰时段另乘 ×Y
首 Token 阈值（秒）
```

只在打开动态倍率时显示阈值输入。未启用本地高峰倍率时不显示“高峰时段另乘”部分。

## 复用现有倍率探测

本功能不增加新的探测线程、周期、协议、数据格式或全局设置。继续使用现有：

- `UpstreamBillingProbeService`。
- 全局自动探测开关和 30 分钟默认周期。
- 账号级 `upstream_billing_probe_enabled`。
- 单账号及批量手动探测能力。
- `accounts.extra.upstream_billing_probe` 中的现有快照、有效期和失败保留规则。

开启动态倍率或将 API Key 账号加入已开启的分组时，可直接调用现有的账号探测开启和批量探测能力进行一次初始刷新，但不复制其实现。现有 `ProbeAccounts` 单批最多处理 20 个账号，调用方必须按该上限分批提交，不能静默截断大分组。这是管理操作后的异步最佳努力任务：没有可沿用的新鲜成功快照且初始探测失败时，不回滚分组开关，该账号先作为未验证兜底账号。

探测失败时沿用现有失败保留规则：如果上一次成功快照仍在 `fresh_until` 内，账号继续作为已验证中转参与排序和计费，同时管理端显示“本次探测失败，沿用上次有效结果”；只有没有可沿用快照或快照过期后，账号才降为未验证兜底。

分组保存页必须检查全局自动探测开关和该分组 API Key 账号的账号级探测开关。全局探测关闭不阻止保存，也不阻止本次手动初始刷新，但必须显示明确警告：初始快照过期后账号将自动降为未验证，动态倍率会退化为基础倍率按上限计算，之后仍按现有规则乘本地高峰因子。账号级探测关闭时同样显示账号数量和警告，并允许管理员跳转处理。

关闭某个分组的动态倍率时，不自动关闭账号级探测，因为同一账号可能还被其他分组使用。

## 全局首 Token 样本

### 样本口径

每个 OpenAI 账号按“实际使用的上游传输”分别维护全局窗口，至少区分 `http_sse` 和 `responses_ws`，同一传输内不区分模型、分组或渠道分类。同一账号被多个分组使用时共享真实上游性能样本，不能为每个分组重复建窗。样本必须同时满足：

- 请求属于全局首 Token 优化范围内的文本流式请求。
- 上游请求成功。
- `upstream_first_token_ms > 0`。
- 不是客户端主动取消。
- 能明确关联到实际承接的账号。
- 能明确关联到本次实际使用的上游传输。
- 首个计时终点是可展示文本、内容 Token 或工具参数 delta，而不是前导或终止事件。

所有传输使用同一业务定义：从本轮实际请求即将写给上游的时刻开始，到收到第一个可展示的内容 Token、文本或工具参数 delta 为止。HTTP 在调用上游请求前开始计时；Responses WebSocket 在写入该轮 `response.create` 前开始计时。连接池选择、账号排队和用户在长连接中的空闲时间不计入上游 TTFT；`response.created`、心跳、元数据、role-only、usage-only 和终止事件都不能作为首 Token。现有 WebSocket 每轮计时必须先修正为在 `response.create` 写入时建档，不能在首次收到带 `response_id` 的上游事件时才建档。

窗口规则：

- 只保留最近 24 小时内最新 10 条有效样本。
- 超过 24 小时的样本失效。
- 新样本加入后，超过 10 条时淘汰最旧样本。
- 有效样本达到 10 条后才认为统计成熟。

百分位使用确定性 nearest-rank 规则：将 10 条数据按耗时从小到大排序，P50 取第 5 条，P90 取第 9 条。因此单次尾部抖动不会立即将 P90 推高，但最近 10 次中出现至少约 2 次慢请求时会反映到 P90。

### 预热和持续更新

- HTTP、WebSocket ingress、WebSocket passthrough 和桥接路径必须完整回填 `upstream_first_token_ms`、`client_disconnected` 和实际传输；历史预热必须依赖这些字段排除客户端主动取消和口径不明数据。旧数据不得假定为“未取消”或把原 `first_token_ms` 直接当作上游 TTFT，默认不纳入首批成熟判定。
- 启用全局首 Token 优化、开启动态倍率、服务启动、Redis 恢复或样本缓存丢失时，在后台按“账号 + 上游传输”从用量日志加载最近 24 小时内最新 10 条有效样本。
- 这个历史查询不得在每个用户请求中执行。
- 后续每个流式请求结束后，使用有界异步任务将新样本写入滚动窗口，不阻塞当前响应。样本任务与用量落库共享请求级事实，但任一方失败不得阻止另一方执行；任务丢弃或写入失败必须记录指标和结构化告警，Redis 恢复后通过历史预热补齐。
- Redis 有序集合成员必须包含唯一请求标识和样本时间。一次 Lua 脚本或等价原子操作完成：删除 24 小时前样本、按样本时间加入、裁剪到最新 10 条、设置至少 25 小时键 TTL，并返回样本数/P50/P90。异步任务乱序完成不能改变“最新 10 条”的定义。
- 样本以 Redis 作为多实例共享存储；Redis 不可用时允许使用进程内缓存，但必须禁用探索，普通分组回退到手工优先级/负载/LRU，动态倍率分组回退到低倍率优先，避免多实例重复探索。Redis 恢复时主动从用量日志重建当前所有可调度 OpenAI 账号的窗口，共享窗口恢复前不重新开启探索。

### 探索流量

样本不足 10 条的可调度账号为“待观察”，但主动探索的候选范围取决于调度模式：

- 普通分组只探索当前最高手工优先级层内的可用 OpenAI 账号，账号可以是 OAuth、官方 API Key、中转或尚未验证的 API Key；不得为了采样越过管理员设置的优先级。
- 动态倍率分组只探索参与动态排序的已验证中转账号。OAuth、未验证 API Key 和不兼容账号仍可从正常兜底请求被动积累样本，但不能主动占用动态倍率探索流量。

共同规则如下：

- 只使用无粘性的新流式会话探索。
- 每个 `group_id + 调度模式 + 当前优先级层 + 上游传输` 使用 Redis 原子累计配额控制探索资格；动态倍率模式将被忽略的手工优先级归一为固定层。5% 配置最多允许累计 1/20 的符合探索前置条件请求，不使用各实例独立随机数。
- 待观察账号之间轮转获得探索机会。
- 探索并发锁和冷却状态按 `group_id + account_id + 上游传输` 隔离，因为不同分组阈值可能不同。同一目标最多同时承接 1 个探索请求。
- 探索锁使用带随机令牌的 Redis 租约，TTL 覆盖单请求最大执行时间并支持续租；只有持有相同令牌的请求可释放，防止超时请求误删新锁。
- 任一探索请求出现可重试错误，或上游 TTFT 超过当前有效稳定门槛，立即停止该账号在该分组/传输下的探索 5 分钟，不必等满 10 个差样本。普通分组使用全局 5 秒门槛，动态倍率分组使用自己的门槛。
- 已成熟且 P90 超过阈值的账号进入“性能隔离”。除兜底或正常请求样本外，每 30 分钟最多获得 1 次恢复探索机会，仍占用分组 5% 总探索额度且遵守单账号并发 1；滚动窗口重新满足 P90 阈值后自动恢复。

5% 是主动把本可由正常候选承接的请求分流给待观察/恢复账号的上限，不是强制比例。没有探索目标、存在任何强/软会话粘性、探索并发已占用或共享缓存不可用时，不发生探索。普通分组没有成熟合格账号时按当前最高优先级层内的最优可用兜底执行；动态倍率分组按最低倍率兜底执行。这些保证可用性的正常选择不计为探索，即使选中账号尚未成熟，产生的有效样本仍进入全局窗口。

## 全局首 Token 调度策略

### 普通分组流式请求

普通分组是指未开启动态倍率，或当前请求不适用动态倍率的分组。选择顺序如下：

1. `previous_response_id` 对应账号是强粘性。账号仍合法且上下文不能安全迁移时必须继续使用，不能为了首 Token 或负载切换。
2. `session_hash` 是软粘性。账号样本尚未成熟或当前传输 `P90 <= 全局稳定门槛` 时保持粘性；只有样本成熟且 P90 持续超标、账号进入错误冷却或不再合法时，才允许解除软粘性。解除后仍不得越过原本可用的最高手工优先级层。
3. 依次执行账号活动状态、可调度、模型/端点/传输能力、限流、配额暂停、并发和重试排除检查。
4. 只保留当前数值最小的手工优先级层；低优先级账号只有在更高优先级层无可用账号时才能进入。
5. 除受控探索外，优先选择样本成熟且当前传输 `P90 <= 全局稳定门槛` 的账号，按 P90、P50、当前负载、队列和账号 ID 依次升序破平。
6. 如果没有成熟且 P90 合格的账号，选择成熟账号中 P90 最低者；如果全部未成熟，沿用当前优先级层内现有负载/LRU 顺序，不因样本不足拒绝服务。

全局首 Token 优化是流式请求的确定性性能分层。现有高级调度的错误率、负载和队列能力继续参与资格判断或同层破平，但 TTFT EWMA 权重不得再次改变上述 P90/P50 顺序；普通流式请求的 `sticky escape` 同样改用成熟 P90，而不是 EWMA 瞬时值。非流式请求完全沿用现有手工优先级、负载、队列和故障切换，不读取 P90/P50。

### 与动态倍率的组合

动态倍率请求复用同一份“账号 + 实际上游传输”P90/P50 窗口、语义事件判定、连接池和首输出长尾保护，但账号排序仍按后文动态倍率规则执行：已验证中转范围内先满足 P90 门槛，再选择最低上游实际倍率。动态倍率已确认的强/软粘性语义保持不变，其流式请求禁用基于 P90、EWMA 或错误率加权分数的主动 `sticky escape`；只有账号不合法、粘性等待超时或实际请求发生可重试失败后才切换。

### 调度快照

一次账号选择必须读取同一时刻的候选资格、优先级、P90/P50、当前负载、队列、探索资格和冷却状态，形成只读调度快照。排序期间不得逐账号同步查数据库或历史用量表。账号并发槽位取得后仍需按现有规则重新确认账号合法性；如果资格变化则释放槽位并重新选择，不能使用过期调度结果强行转发。

## 全局传输优化和首输出长尾保护

### HTTP/2 和连接复用

- 继续默认启用现有 OpenAI HTTP/2 策略、上游客户端缓存和连接池；代理明确不兼容时才沿用现有熔断回退 HTTP/1.1。
- 连接池键必须包含现有安全隔离所需的 Base URL、代理和账号维度。禁止为了提高命中率把凭据、代理或会话隔离要求不同的账号合并到同一不安全客户端。
- 每次请求复用缓存客户端和空闲连接，不在热路径重复创建 `http.Client`、解析代理或执行可缓存的 TLS 配置构造。
- 本期不发送 HEAD、空 prompt 或其他虚假模型请求预热 HTTP。冷连接按正常请求建立并计入连接获取耗时，后续由连接池自然复用。

### Responses WebSocket 预热

- 继续使用现有账号级连接池、并发派生上限、最小空闲连接、失败抑制和冷却机制；只对近期有真实 WS 流量或当前存在排队请求的可调度账号维持配置允许的空闲连接。
- 预热只完成 DNS、TCP、TLS、WebSocket 握手和必要鉴权，不发送 `response.create`，也不启用 `generate=false` 模型预热；现有 `prewarm_generate_enabled` 保持 `false`。
- `store=false`、强会话隔离、代理隔离和账号隔离高于连接复用。无法证明连接可安全复用时必须新建连接，不能为了降低 TTFT 复用可能携带其他会话状态的连接。
- 连接池满、预热失败或预热被抑制时回退正常建连，不把账号直接判为不可用。预热任务必须有并发上限、超时和代际保护，账号禁用、凭据更新或代理变化后关闭旧连接并使在途预热结果失效。

### 首输出长尾切换

首输出长尾切换复用现有首输出暂存和可切换错误机制，最终目标阈值为普通推理 30 秒、`high/xhigh/max` 120 秒。规则如下：

1. 从请求真正写给上游时开始计时，本地路由、账号排队、连接获取和 WebSocket 空闲时间不计入 30/120 秒。
2. 在首个语义内容前暂存上游响应头和非语义前导事件。允许发送的只能是网关生成、协议合法且不携带上游账号状态的中性心跳；心跳不能结束计时、生成样本或阻止内部安全切换。传输无法保证心跳后仍可安全切换时必须暂存而不是发送。
3. `response.created`、role-only、元数据、usage-only、心跳和终止事件都不是语义输出；首个文本、内容 Token 或工具参数 delta 到达后立即停止计时、提交暂存内容，并永久禁止本次请求再因 TTFT 切换。
4. 只有请求体已经完整缓冲且可重放、未向客户端发送语义内容、客户端仍连接、没有 `previous_response_id` 强粘性且端点不属于图片/Live/Realtime 时才允许切换。无法明确证明可安全重放时不切换，沿用原请求结果或现有错误语义。
5. 超时后先取消原上游上下文、释放连接/并发资源、把原账号加入本次排除集并记录超时冷却，再串行选择另一个账号。禁止第二个请求在第一个仍被本地持有时并发启动。
6. 每个用户请求最多发生 1 次首输出超时切换。第二个账号仍超时或失败时返回现有错误，不得发起第三次请求。
7. 账号切换后重新生成账号调度结果和动态倍率计费快照；用户只按最终成功响应计费一次。首个超时尝试可能形成但无法确认的上游成本，必须以独立管理员指标和审计事件记录，不能叠加到用户 Token 用量。
8. 客户端断开时立即取消当前上游，不再切换，不产生有效 TTFT 样本。

禁止任何形式的并发双发、先到先赢或后台继续保留已失败尝试。30/120 秒只处理极端无输出长尾；5 秒稳定门槛只影响下一次请求排序，两者不能合并。

## 动态倍率调度策略

### 请求适用性判定

动态倍率是否适用必须在账号选择前确定，不能等请求结束后根据结果反推。判定输入包括分组开关、平台、入站端点、请求意图以及当前已解析的渠道计费模式：

- 适用：OpenAI 平台下按 Token 计费的 Chat Completions、Completions、Responses、Responses WebSocket、`/responses/compact`、Embeddings，以及分发到 OpenAI 账号的 `/v1/messages`。
- 图片请求只有在渠道定价明确为 Token 模式时适用；按次或 image 模式不适用。
- Alpha Search、网页搜索按次、图片/视频按次、Live/Realtime、仅模型列表或 token 计数等不产生 OpenAI Token 扣费的请求不适用。
- 请求在选择前无法可靠判定计费模式时，安全回退到原调度和固定基础倍率上限，不得先按动态倍率选择、结束后再追溯改价。

调度器接收显式的 `dynamic_rate_applicable` 和上游传输类型，避免各 handler 自行猜测。即使同一账号既支持 HTTP 又支持 WebSocket，也只读取当前请求对应传输的样本窗口。

### 通用前置规则

以下现有规则始终优先：

1. 必要的 `previous_response_id` 和 `session_hash` 会话粘性。
2. 账号活动、可调度、未过期、未冷却。
3. 请求模型、传输方式、端点和能力匹配。
4. 限流、配额自动暂停、并发槽位和排队约束。
5. 重试过程中已失败的账号排除集。

`previous_response_id` 属于强粘性；`session_hash` 属于软粘性。动态倍率开启时，如果粘性账号通过账号状态、能力、传输、限流和并发等合法性检查，继续使用它，即使它不是最低倍率，最终计费按实际选中账号处理。为保证本规则与现有实现一致，动态倍率分组必须禁用基于历史 TTFT、历史错误率和全局加权分数的 `sticky escape`；账号并发已满时沿用现有粘性等待，等待超时或账号变为不合法后才允许切换。强粘性无法安全迁移时继续沿用现有错误语义，不为了价格或性能重放上下文。

### 非流式请求

非流式请求不判断首 Token，只要账号未被现有异常、限流、冷却、并发和能力规则排除，就可以使用。在所有合格的已验证中转中：

1. 上游实际倍率低者优先。
2. 倍率相同时选择当前负载和队列更优者。
3. 动态倍率模式下不使用账号手工优先级。
4. 前述条件仍相同时，以账号 ID 作为最后的稳定破平键，保证多实例在相同快照下顺序一致。

如果最低倍率账号的实际转发返回现有重试分类认定的可重试异常，本次请求排除该账号，沿用现有冷却/限流状态，然后选择第二低倍率账号。客户端参数错误等不可重试错误不得通过换账号重试。

### 流式请求

除了少量受控探索请求，正常流式选择使用以下规则：

1. 从合格的已验证中转中找到样本成熟且 `P90 <= 分组首 Token 阈值` 的账号。
2. 如果存在合格账号，选择上游实际倍率最低者。
3. 倍率相同时，依次比较当前上游传输的 P90、P50、当前负载和队列。
4. 如果没有任何成熟且 P90 合格的账号，不拒绝请求，回退到全部合格中转中的最低倍率账号。

该规则等价于“先看低倍率，低倍率账号首 Token 不合格时换第二低倍率，全部不合格时仍低倍率优先”。

首 Token 判断只使用同一上游传输的历史数据，影响后续请求。调度器不会在当前请求中先等待阈值再换账号，也不会在已向客户端输出内容后重放请求。

### 中转全部不可用

所有已验证中转都被现有账号规则排除时，允许使用 OAuth、官方直连或未验证账号作为最终兜底。兜底选择继续使用现有调度和故障切换规则，不使用上游动态倍率和 P90/P50。

## 计费规则

### 上游实际倍率

对已验证中转，使用账号选中时现有探测快照解析出的当前有效倍率。该倍率是上游返回的 `effective_rate_multiplier` 语义，包含上游自身的用户专属倍率和当前高峰规则。现有探测快照携带高峰时间表时，可继续使用现有逻辑按当前时间重算。

不使用本地 `accounts.rate_multiplier`。该字段仍用于原有账号统计成本口径。

### 用户倍率公式

对最终选中已验证中转的 OpenAI Token 计费请求：

```text
base_cap = user_group_rate_override ?? group.rate_multiplier
base = min(upstream_effective_rate_multiplier * 2, base_cap)
final = base * group.PeakMultiplierAt(captured_at)
```

示例：

```text
上游倍率 0.03，基础倍率上限 0.08 -> 基础倍率 0.06
上游倍率 0.05，基础倍率上限 0.08 -> 基础倍率 0.08
基础倍率 0.08，本地高峰因子 1.5 -> 最终倍率 0.12
```

本地高峰因子仍只按现有订阅分组规则生效，并在动态基础倍率之后相乘。

如果最终使用的是 OAuth、官方直连或未验证账号，则不进入动态公式：

```text
base = base_cap
final = base * group.PeakMultiplierAt(captured_at)
```

### 计费范围

动态公式仅替换 OpenAI Token 计费路径的基础倍率。

- Chat、Responses、Responses WebSocket、`/responses/compact`、Completions、Embeddings、分发到 OpenAI 的 Messages 等 Token 计费使用动态倍率。
- 图片渠道如果明确使用 Token 计费，继续属于 Token 路径。
- 图片、视频按次计费继续使用现有独立价格和倍率。
- 网页搜索按次计费继续使用现有基础倍率口径。
- 标准余额分组和订阅分组都可开启动态倍率。

### 数值精度

- 探测倍率、用户专属倍率、分组倍率、基础倍率、本地高峰因子和最终倍率在进入比较或公式前，统一量化为小数点后 8 位，使用明确的十进制 `ROUND_HALF_UP`；不得直接用未经量化的 `float64` 做扣费或相等判断。
- `usage_logs.rate_multiplier` 和 `usage_logs.account_rate_multiplier` 迁移为至少 `DECIMAL(20,8)`。扣费、额度累计、用量日志和审计上下文必须使用同一个量化后的最终倍率。
- JSONB 审计上下文中的倍率使用固定精度十进制字符串，例如 `"0.06666600"`，避免 JSON 浮点往返改变数值。界面显示时可去除无意义的尾零，但不得改变实际数值。
- 倍率相同是指量化后的十进制值相同。所有排序在最后使用账号 ID 稳定破平。

## 不可变计费快照

账号候选被选中且账号并发槽位真正获取成功后，在实际转发前重新确认账号合法性和探测快照在 `captured_at` 仍然有效，然后立即生成请求级快照。等待计划返回时不得提前生成；如果排队期间快照过期，账号降为未验证兜底或重新选择其他已验证中转。快照至少包含：

- 是否开启动态倍率。
- 最终选中账号和渠道分类。
- 倍率来源：已验证探测或上限兜底。
- 上游实际倍率（若适用）。
- 探测收到时间和有效期（若适用）。
- 分组倍率、用户专属倍率和基础倍率上限。
- 基础倍率、本地高峰因子和最终倍率。
- 快照时间 `captured_at`。

账号选择前的基础资格检查、RPM/并发检查只能使用现有分组和订阅状态，因为此时尚未知道最终账号，不属于动态倍率快照消费者。账号选定后的金额相关路径必须将快照作为显式参数传入：

- 与金额相关的余额、订阅 USD 限额和平台额度累计。
- 余额扣减。
- 订阅额度消耗。
- `CostBreakdown.ActualCost` 计算。
- 用量日志。

异步计费任务不得重新查询当前分组倍率、当前探测倍率或当前高峰时段。这保证请求执行期间配置变化不会造成“按一个倍率选择，按另一个倍率扣费”。快照对象必须随所有异步用量任务传递，禁止只传账号 ID 后在 worker 中重建。

发生可重试失败并切换账号时，旧快照作废，为最终实际承接请求的账号重新生成快照。一旦已将流式内容发送给客户端，不为调度优化重放请求。

## 用量日志和审计

`usage_logs.rate_multiplier` 继续存储用户最终实际倍率。`usage_logs.account_rate_multiplier` 继续保留现有账号统计口径，不改成上游探测倍率。

所有属于全局首 Token 优化范围且能够明确最终账号的用量记录写入可空、版本化的 `openai_ttft_context JSONB`。它用于管理员逐请求排障，不参与金额计算；最小版本 1 如下：

{

  "transport": "http_sse",
  "user_first_token_ms": 824,
  "routing_ms": 3,
  "queue_wait_ms": 11,
  "connection_acquire_ms": 5,
  "upstream_first_token_ms": 805,
  "connection_reused": true,
  "exploration": false,
  "sample_count": 10,
  "sample_p50_ms": 760,
  "sample_p90_ms": 980,

没有产生有效语义首 Token 的失败、超时或客户端取消请求仍写入已知的延迟分解和原因，但 `upstream_first_token_ms` 置空且不得进入样本窗口。发生首输出切换时，最终成功用量记录写入 `switch_count=1` 和首个账号 ID；首个超时尝试另写管理员审计事件，不创建第二条用户计费用量。字段只允许向后兼容地追加。

为避免为未来快照字段反复添加列，在用量日志增加可空、版本化的 `openai_rate_context JSONB`。所有能够明确最终账号的 OpenAI 用量记录都写入基础渠道分类；已验证中转无论动态倍率是否开启，都写入本次请求捕获的上游实际倍率。动态倍率适用时再写入完整计算快照。最小版本 1 结构如下，字段只允许向后兼容地追加：

```json

  "user_group_rate": null,
  "base_cap": "0.08000000",
  "base_rate": "0.02000000",

  "final_rate": "0.02000000",
  "selection_reason": "lowest_rate_p90_qualified",

```

`channel_class` 至少支持 `verified_relay`、`official_oauth`、`unverified_api_key` 和 `incompatible`。探测失败但仍沿用新鲜成功快照时仍为 `verified_relay`，同时将 `rate_source` 记为 `retained_fresh_probe`。非动态请求不伪造动态计算字段，可将其置空并保留实际渠道、上游倍率和捕获时间。

普通用户 DTO 不得新增返回账号类型、上游倍率、探测时间和内部倍率计算过程；现有 `account_id` 为保持 API 兼容继续保留，本期不顺带删除。管理员 DTO 可返回完整上下文用于账单解释和问题排查。普通用户列表、详情、导出和统计接口都不得透传 `openai_ttft_context` 或 `openai_rate_context`。

## 用户和管理界面

### 分组管理

- 不增加“首 Token 优化”分组开关或独立功能入口；该能力由系统全局提供。分组页面只保留动态倍率及其阈值配置。
- 在现有分组新建/编辑表单显示“动态倍率”开关。
- 开关下方显示备注“仅适用于上游中转渠道”。
- 开启时显示“首 Token 阈值”数字输入，后缀为“秒”。
- 复制分组时复制开关和阈值。
- 开启动态倍率的分组不删除账号手工优先级，只在该分组的请求中忽略它；该分组的账号优先级控件置灰并说明由动态倍率接管。关闭后恢复编辑和原值，再次开启时继续保留原值。

### 管理员账号和用量视图

管理员可看到：

- 渠道判定：已验证中转、OAuth/官方账号、未验证或不兼容。
- 上游实际倍率、探测状态、收到时间和有效期。
- 账号最近 24 小时按上游传输分开的有效首 Token 样本数、P50 和 P90。
- 管理员请求详情可查看用户感知 TTFT、路由、排队、连接获取、上游 TTFT、冷/热连接、是否探索、是否发生首输出超时切换及切换原因；普通用户 DTO 不返回内部账号和调度明细。
- 管理员使用记录列表和详情显示该请求实际采用的“上游中转倍率”。`verified_relay` 显示实际倍率；`official_oauth` 显示“未使用中转”；`unverified_api_key` 或 `incompatible` 显示“倍率未验证”，不得据此断言不是中转。该字段仅由管理员 DTO 返回。
- 显示格式为 `上游中转倍率：{上游实际倍率}x`，即标签后跟本次请求对应的上游实际倍率，例如实际倍率为 `0.01` 时显示 `上游中转倍率：0.01x`；不换算成百分比，也不显示乘以 2 后的基础倍率或用户最终计费倍率。
- 用量详情中的动态计费快照和最终选择原因。

### 普通用户

- 分组、套餐和密钥页面显示“动态倍率，基础倍率最高 ×X”；本地高峰倍率启用时追加“高峰时段另乘 ×Y”，不得显示成无条件的最终最高倍率。
- 用量明细继续显示每次请求的实际最终倍率。
- 不显示上游账号、上游成本倍率、P50/P90 或内部调度原因。

## 与现有调度开关的关系

- 全局首 Token 优化与动态倍率开关无关。内部 `gateway.openai_ttft_optimizer_enabled` 开启后，所有适用的普通分组文本流式请求在不越过手工优先级的前提下使用 P90/P50；关闭内部发布门时立即恢复原流式调度，但继续保留指标采集用于排障。
- 非流式请求不使用 P90/P50，继续沿用现有 OpenAI 调度开关、实验调度策略、账号优先级/权重和固定分组倍率计费。
- 全局首 Token 优化接管流式性能分层后，现有高级调度的 TTFT EWMA 权重和 EWMA `sticky escape` 对流式请求必须失效，避免同一性能信号重复排序；负载、队列、错误冷却和资格过滤继续生效。
- 分组开启动态倍率后，只有“请求适用性判定”确认适用的请求由动态倍率策略接管低倍率排序和计费；它仍复用全局首 Token 样本、连接优化和首输出长尾保护。图片/视频/搜索按次、Live/Realtime 等不适用请求仍走原计费。
- 对适用请求，本设计的确定性分组策略替代账号手工优先级以及基于历史 TTFT、历史错误率或全局加权分数的主排序，不能让高倍率账号仅凭权重排在 P90 合格的低倍率账号前。
- `previous_response_id` 强粘性和 `session_hash` 软粘性仍按“通用前置规则”优先；动态倍率分组禁用 TTFT/错误率加权触发的 `sticky escape`，但保留账号不合法、等待超时和可重试失败时的正常切换。
- 本策略继续复用现有账号资格、能力匹配、并发、负载、队列、限流、冷却和故障切换；这些规则不是动态倍率排序的一部分，但始终先决定账号是否可用。
- 现有全局开关、账号优先级和权重配置不删除。动态倍率开启期间仅忽略并置灰该分组的账号优先级配置，关闭后立即恢复原值和原行为。

## 故障处理和降级

- 全局首 Token 优化内部发布门关闭：普通流式请求恢复上线前账号调度；连接池继续按现有配置工作，P90/P50 不影响选择。
- 上游 TTFT 或客户端断开字段缺失：该记录不进入成熟窗口，不得回退使用口径不明的旧 `first_token_ms` 猜测。
- 历史样本预热失败：账号作为待观察，不在请求链路同步查库；后台按退避策略重试并记录结构化告警和失败指标。普通分组按手工优先级/负载/LRU，动态倍率分组按低倍率可用性兜底。
- Redis 不可用：禁用全部探索，可使用进程内样本做最佳努力排序；普通分组数据不足时回到原调度，动态倍率分组数据不足时低倍率优先。Redis 恢复后触发所有可调度 OpenAI 账号的历史重建，共享窗口恢复前继续禁用探索。
- HTTP 连接池或 WebSocket 预热失败：回退正常冷连接；只有正常建连也失败时才沿用现有错误分类、冷却和账号切换，预热失败本身不能暂停账号。
- 首输出超时但请求不可安全重放：不切换账号，沿用原请求结果或现有错误语义，并记录“跳过不安全切换”的原因。
- 首输出超时已切换一次：第二个账号失败后立即停止，不允许第三次请求；客户端断开时也立即停止。
- 首个超时尝试可能产生未知上游费用：记录管理员审计和疑似重复成本指标，用户只按最终成功响应计费一次。无法可靠确认最终成功账号和计费快照时进入计费重试/人工核对，不能重复扣费。
- 倍率探测失败：不阻塞分组保存或用户请求。上一次成功快照仍在 `fresh_until` 内时继续沿用并标记 `retained_fresh_probe`；只有不存在可沿用快照或快照过期后，账号才降为未验证兜底。
- 调度样本数据异常：忽略非法耗时并保留最近合法窗口。
- 可重试上游失败：延用现有错误分类、排除集和冷却逻辑，按调度顺序选下一账号。
- 所有已验证中转不可用：使用非中转/未验证账号兜底，基础倍率按用户/分组上限计算，之后仍按现有规则乘本地高峰因子。
- 用户专属倍率查询失败：沿用现有缓存和安全回退规则，不使用上游倍率扩大用户价格上限。
- 计费快照缺失：对动态倍率请求使用请求上下文中已确定的基础倍率上限作为 `base`，再乘同一请求已捕获的本地高峰因子，并记录包含请求、分组和账号标识的结构化告警，不可默认为 1 倍或 0 倍。如果连基础倍率上限或高峰因子也无法可靠取得，则计费任务进入可重试/人工核对队列并触发高优先级告警，不得猜测金额。

## 性能约束

- 用户请求不同步调用上游倍率接口。
- 用户请求不同步扫描用量日志。
- 探测倍率、P50/P90 和探索状态均从调度快照或 Redis/进程内缓存读取；同一次选择使用批量读取或本地快照，候选排序不得对每个账号重复访问数据库或产生与账号数线性增长的 Redis 往返。
- 流式请求结束后的样本更新通过有界异步任务执行；队列满、任务丢弃或 Redis 写入失败不得阻塞响应，但必须可观测并可通过历史重建补齐。
- Redis 样本更新使用一次原子操作完成清理、写入、裁剪、续期和统计返回；探索资格、租约获取/续租/释放也必须使用有界次数的 Redis 操作，避免候选数扩大请求时延。
- 开启动态倍率或账号加入分组后的初始倍率探测是后台任务，并严格按每批最多 20 个账号提交；大分组不得在保存请求中串行等待全部探测完成。
- HTTP 不发送合成模型请求预热；WebSocket 预热任务使用既有并发上限、超时、失败抑制和代际保护，不能因账号数量增长无限创建连接或 goroutine。
- 服务启动、Redis 恢复和缓存丢失后的历史重建在后台分批限速执行，不能形成用量数据库查询洪峰，也不能阻塞用户请求。
- 全局首 Token 优化与动态倍率合计带来的新增调度耗时目标为 P95 小于 5 毫秒。

5% 探索可能让极少量请求进入尚未验证速度的账号，这是获得第二、第三账号真实首 Token 数据的必要成本。历史日志预热、无粘性限制、单账号探索并发 1 和首次差样本立即冷却用于限制用户体验风险。

## 测试策略

### 全局适用范围和计时

- 全局首 Token 配置拒绝越界、非整数和非有限值；灰度比例使用稳定哈希，多实例对同一请求得到相同结果。
- Chat Completions、Completions、Responses SSE、Responses WebSocket、`/responses/compact` 流式桥接和分发到 OpenAI 的 Messages 流式请求进入全局首 Token 优化。
- 非流式请求只复用连接，不读取 P90/P50、不产生样本、不探索且不执行首输出超时切换；图片、视频、搜索按次、模型列表、token 计数和 Live/Realtime 全部排除。
- `usage_logs.first_token_ms` 原有 API 语义保持不变；新增 `upstream_first_token_ms` 和 `client_disconnected` 在所有 HTTP、WS ingress、WS passthrough 和桥接路径完整落库。
- HTTP 从请求即将写给上游开始计算上游 TTFT；Responses WebSocket 从该轮 `response.create` 即将写入开始，排除本地路由、排队、连接获取和长连接空闲时间。
- 首个文本、内容 Token 或工具参数 delta 结束计时；响应头、SSE 建连、`response.created`、role-only、心跳、元数据、usage-only 和终止事件均不能结束计时。
- 缺少新字段或计时起点不明的旧用量记录不能让窗口变为成熟；客户端在首 Token 前或流式过程中主动断开均不产生合格样本。

### 普通分组调度

- `previous_response_id` 强粘性不因性能迁移；软粘性在样本未成熟或 P90 合格时保持，在成熟 P90 超标时只能逃逸到同一最高手工优先级层。
- 普通流式请求始终先选择数值最小的手工优先级层，不能让低优先级账号凭更快 P90 越级。
- 同优先级内优先选择成熟且 P90 不超过 5 秒的账号，再按 P90、P50、负载、队列和账号 ID 稳定破平。
- 没有成熟合格账号时选择成熟账号中 P90 最低者；全部未成熟时恢复现有负载/LRU，不拒绝服务。
- 全局优化关闭时恢复上线前流式调度；开启时 TTFT EWMA 权重和 EWMA `sticky escape` 不得再次改变 P90/P50 排序。
- 非流式请求保持原手工优先级和高级调度行为。

### 连接和首输出切换安全

- HTTP/2 客户端被安全复用，Base URL、代理、凭据或隔离策略不同的账号不能误共享客户端；HTTP 预热不得发出任何模型请求。
- WebSocket 预热只完成连接和鉴权，不发送 `response.create`/`generate=false`；`store=false`、代理、账号和会话隔离测试覆盖池命中与池未命中。
- 账号禁用、凭据更新或代理变化时，旧 WS 连接被关闭，在途预热结果因代际不匹配而丢弃；预热失败回退冷连接且不暂停账号。
- 普通推理使用 30 秒、高推理使用 120 秒；计时从实际写上游开始，前导事件和网关心跳不能解除超时保护。
- 首个语义输出到达后立即提交暂存并永久禁止切换；超时前已发送的协议心跳不能泄漏上游账号状态或导致重复响应头。
- `previous_response_id`、请求体不可重放、客户端已断开、已输出语义内容和排除端点均跳过切换。
- 可安全切换时先取消并释放第一个尝试，再串行启动第二个账号；并发探针证明任意时刻最多只有一个本地持有的上游尝试。
- 每个请求最多切换一次；第二个账号失败后不发第三次请求。首个尝试加入本次排除集并进入正确冷却。
- 用户用量和动态倍率快照只采用最终成功账号一次；首个超时尝试仅形成管理员审计和疑似重复上游成本指标。

### 分组和 API

- 新建分组默认关闭动态倍率，阈值默认 5000 毫秒。
- 创建、编辑、详情、列表和复制正确保存两个字段。
- 拒绝小于 1 秒、大于 60 秒、非整数或非有限数的阈值。
- 分组缓存、API Key 上下文和调度快照能在配置更新后及时失效。

### 渠道判定和探测复用

- RT JSON 导入账号被识别为 OAuth 并排除于动态排序。
- 具有新鲜合法 Sub2API 快照的 API Key 被识别为已验证中转。
- 官方 API Key、不兼容中转、没有成功快照或成功快照已过期的 API Key 只作为兜底。
- 本次探测失败但上一次成功快照仍然新鲜时继续识别为已验证中转；超过 `fresh_until` 后自动降为未验证。
- 探测结果解析出的倍率必须严格大于 0；零倍率、负数、非有限数或超出十进制定点范围的结果不得进入动态排序和计费。
- 动态倍率复用现有有效期和上游高峰重算规则。
- 开启分组时的初始探测调用现有服务，不创建第二个周期任务；含 21 个以上 API Key 的分组按每批最多 20 个账号完整提交且不静默遗漏。
- 全局或账号级自动探测关闭时仍允许保存和手动初始探测，但管理端显示对应警告、受影响账号数和处理入口。

### 动态倍率调度

- `dynamic_rate_applicable` 对 Chat、Completions、Responses、Responses WebSocket、`/responses/compact`、Embeddings 和分发到 OpenAI 的 Messages 判定为真；对按次图片/视频/搜索、Live/Realtime、模型列表和 token 计数判定为假。无法在选号前可靠判断计费模式时回退原调度和固定基础倍率上限。
- 非流式请求选择最低倍率的无异常可用账号。
- 最低倍率账号返回可重试异常时切换到第二低倍率账号。
- 不可重试的客户端错误不切换账号。
- 流式请求在最低倍率账号 P90 合格时使用该账号。
- 最低倍率账号 P90 超标时选择下一个倍率低且 P90 合格的账号。
- 全部成熟账号 P90 超标时回退到最低倍率。
- HTTP SSE 只读取 `http_sse` 窗口，Responses WebSocket 只读取 `responses_ws` 窗口；同一账号两种传输的 P90 不得互相污染。
- 倍率相同时按当前传输的 P90、P50、负载、队列和账号 ID 稳定破平。
- `previous_response_id` 强粘性和 `session_hash` 软粘性账号可用时保持粘性，不为低倍率破坏会话；动态模式下不得因 TTFT、错误率或实验调度加权分数触发 `sticky escape`。
- 中转全部不可用时能够使用 OAuth/官方/未验证账号兜底。
- 动态分组忽略手工账号优先级，关闭动态倍率后恢复原行为。

### 样本和探索

- 历史预热按“账号 + 实际上游传输”分别只取最近 24 小时内最新 10 条有效流式记录，不按模型拆分。
- 非流式、失败、无 `upstream_first_token_ms` 和客户端取消记录不进入窗口。
- 普通分组允许当前最高手工优先级层内的所有 OpenAI 渠道成为探索目标；动态倍率分组只主动探索已验证中转，其他账号只被动积累样本。
- HTTP 从即将发起上游请求时开始计时；Responses WebSocket 必须在写入该轮 `response.create` 前开始计时，不能从首个带 `response_id` 的返回事件开始计时。
- P50/P90 的 nearest-rank 计算正确且稳定。
- Redis 原子样本更新能在并发和异步乱序下完成 24 小时清理、按事件时间写入、只保留最新 10 条、刷新至少 25 小时 TTL，并返回正确的样本数/P50/P90。
- 过期样本被淘汰后，账号恢复为待观察。
- 多实例并发下，Redis 序号仍保证每个 `group_id + 调度模式 + 当前优先级层 + 上游传输` 最多每 20 个符合前置条件的请求产生 1 次探索；只选择无粘性新流式会话，每个 `group_id + account_id + 上游传输` 的探索并发不超过 1。
- 探索租约使用不可猜测令牌，能在长请求中续租，只有令牌持有者可以释放；旧请求超时结束不能删除后来请求持有的新租约。
- 首个探索错误或超阈值样本立即触发 5 分钟探索冷却。
- 成熟慢账号每 30 分钟最多获得 1 次恢复探索，并占用同一 5% 额度；P90 恢复合格后解除性能隔离。
- 普通分组没有成熟合格账号时按最高手工优先级层内的最优可用账号执行，动态倍率分组按最低倍率执行；两者都属于可用性兜底，不消耗探索名额。
- Redis 异常时不重复探索且不阻塞请求；Redis 恢复后触发历史重建，共享窗口恢复后才重新开启探索。

### 计费

- 无用户专属倍率时使用分组倍率作为上限。
- 有用户专属倍率时使用其作为上限。
- 上游倍率为零、负数、非有限数或无法量化时拒绝作为已验证倍率，不能把用户计费降为 0。
- 上游倍率乘 2 低于上限时使用动态结果。
- 上游倍率乘 2 高于上限时按上限计费。
- 本地高峰因子在动态基础倍率之后相乘，最终倍率允许高于基础倍率上限。
- OAuth/官方/未验证兜底的基础倍率按用户/分组上限计算，之后再乘本地高峰因子。
- Token 计费使用动态倍率；按次图片/视频/搜索和 Live/Realtime 不受影响，按 Token 计费的图片请求仍适用。
- 所有倍率按小数点后 8 位和 `ROUND_HALF_UP` 量化；边界值、乘 2、封顶、高峰相乘、相等比较及 JSON 字符串往返保持一致，数据库倍率列至少为 `DECIMAL(20,8)`。
- 余额、订阅额度、限额、成本和日志使用同一快照。
- 请求期间上游倍率或分组配置变化不改变已捕获的请求快照。
- 可重试失败切换账号后重建快照；缺失快照时按基础倍率上限和已捕获高峰因子降级并告警，缺少可靠基础数据时进入重试/人工核对而不是猜测 1 倍或 0 倍。

### 前端

- 分组新建、编辑和复制正确展示动态倍率开关和阈值。
- 阈值的默认值、范围、步进和秒/毫秒转换正确。
- 备注精确显示“仅适用于上游中转渠道”。
- 用户侧显示“动态倍率，基础倍率最高 ×X”，启用本地高峰时追加“高峰时段另乘 ×Y”，并继续显示实际请求倍率；普通用户用量 API、列表、详情、导出和统计均不返回上游中转倍率、`openai_ttft_context` 或 `openai_rate_context`。
- 管理员使用记录列表和详情按 `上游中转倍率：{上游实际倍率}x` 格式展示本次请求对应的上游实际倍率。已验证中转即使未开启动态倍率也显示实际倍率；OAuth 显示“未使用中转”；未验证 API Key 和不兼容账号显示“倍率未验证”。
- 管理员可查看渠道判定、当前传输的 P50/P90、样本数和版本化计费上下文；普通用户不能通过任何 DTO 获得这些字段。
- 动态倍率开启时该分组的账号优先级控件置灰且保留原值；关闭后恢复编辑和原值，再次开启不会丢失配置。

- 记录有效/无效样本数、样本不成熟账号数、Redis 历史重建进度、异步样本任务丢弃/写入失败、探索资格/实际比例、5 分钟冷却和 30 分钟恢复探索。
- 记录 HTTP/2/HTTP1 回退、冷/热连接比例、客户端池命中、WS 空闲/在用/排队连接、预热成功/失败/抑制和因代际变化丢弃的连接。

## 部署和回滚

部署步骤：

1. 先执行 `upstream_first_token_ms`、`client_disconnected`、`openai_ttft_context`、分组新字段、`openai_rate_context` 和倍率列精度迁移，确认新旧版本均可读。
2. 部署向后兼容的新后端并保持全局优化发布比例 `0`、探索比例 `0`、首输出超时 `0`、所有动态倍率关闭。只修正计时和落库，连续采集至少 24 小时基线。
3. 后台重建 HTTP/WS 分离样本并核对语义事件分类。旧数据不满足新口径时允许窗口从零自然成熟，禁止为了加快上线放宽样本合法性。
4. 通过稳定请求哈希把普通分组 P90/P50 排序从小流量逐步扩大；每阶段至少观察一个业务高峰，先验证手工优先级、强/软粘性、错误率和 TTFT 对照指标。
5. 探索比例按 `1% -> 5%` 扩大，验证多实例精确上限、租约、冷却、恢复探索和 Redis 故障自动停探。
6. 启用近期活跃账号的传输连接预热，保持 `prewarm_generate_enabled=false`，核对连接隔离、资源上限、冷/热连接比例和账号/代理变更清理。
7. 在独立小流量实例启用普通 30 秒、高推理 120 秒首输出切换，核对每请求最多一次、无并发双发、强粘性不切换、用户只计费一次和疑似重复上游成本。
8. 全局首 Token 优化通过验收后，再对一个含少量已验证中转的分组开启动态倍率，核对调度决策、用量快照、余额/订阅额度和实际上游费用，最后逐步扩大范围。

回滚必须按层执行：先将首输出超时设为 `0` 停止新切换，再将探索比例设为 `0`，必要时将全局优化发布比例设为 `0` 或关闭内部发布门以恢复原流式调度；动态倍率异常时单独关闭相关分组。已经开始且已产生语义输出的请求继续完成，未开始的预热和探索任务停止接收新任务。新 TTFT 字段、动态倍率字段和历史 `openai_rate_context` 保留；不回退倍率列精度，不删除样本、计费或审计数据。若回滚到不认识新字段的旧后端，必须先验证数据库兼容性，不能直接逆向删除迁移。
