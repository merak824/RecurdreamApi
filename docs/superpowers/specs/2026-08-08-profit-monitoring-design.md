# 实际用量利润监测设计

## 目标

为管理员提供一个“利润监测”页面，按时间范围查看中转站已发生请求的销售额、上游成本、毛利润和毛利率，并按分组、模型、上游账号下钻。成本必须保守、可追溯，不能因为上游自报了较低倍率而静默高估利润。

## 范围

- 销售额采用请求记录中的 `actual_cost`，表示用户实际消耗的站内额度。
- 上游成本采用请求发生时冻结的本地保守成本快照；拿到周期账单后，再在统计窗口层面做结算核对。
- 支持总览、日趋势、分组、模型、上游账号四类统计，支持时间范围和维度筛选。
- 对支持 Sub2API 协议的上游，使用同一 API Key 查询 `/v1/usage`，以累计实际扣费差分为主要结算证据，并用余额、请求数和 Token 数交叉核对。
- 页面标记成本来源：已核验结算、本地审核价、上游声明、历史来源未知。
- 页面只展示监测结果和差异，不发送邮件、不修改账号倍率、不自动触发调度策略。

## 非目标

- 不把兑换码、赠送额度、返利余额和线上支付订单强行合并为现金收入；本功能名称和说明明确为“用量毛利”。
- 不声称可以识别完全由上游伪造的账单。没有余额/账单证据时只能标记为估算。
- 不为非 Sub2API 上游猜测不存在的统一余额接口；结算核对通过明确的协议适配器提供，未匹配适配器的账号保持估算状态。

## 成本可信度策略

### 请求时本地成本

每笔新用量在请求结算时保存一份不可变的本地成本快照。基础价格按以下优先级选择：

1. 管理员配置的账号/分组/模型成本规则。
2. 渠道账号统计定价。
3. LiteLLM/fallback 模型目录价格。
4. 请求标准价 `total_cost`，作为最后兜底。

利润监测为账号维护独立的“审核成本倍率下限”，默认 1.0。请求时有效监测倍率取审核下限和新鲜上游声明倍率的较高值。上游 `/v1/sub2api/billing` 返回的 `resolved_rate_multiplier` 因此可以提高风险成本，但不能降低审核成本。现有账号倍率自动同步功能仍可服务调度和原有账号统计，不直接决定利润监测成本。

```text
请求本地监测成本 = 基础成本 * max(审核成本倍率下限, 新鲜上游声明倍率)
```

管理员确认合同折扣后，可以把审核下限调整为低于 1.0；这个值只允许管理端修改，上游探测不能覆盖。

### 周期结算核对

对探测确认支持 Sub2API 的 API Key 上游，后台按 30 分钟间隔请求：

```text
GET {account.base_url}/v1/usage?start_date=...&end_date=...&days=...&timezone=UTC
Authorization: Bearer {account.api_key}
```

采集资格沿用现有 `upstream_billing_probe_enabled` 显式开关，只覆盖通过现有 base URL 校验的 API Key 账号。不开启探测的账号不会新增网络请求；页面刷新也只会调度已开启账号。

每次保存上游 `usage.total.actual_cost`、累计请求数、累计 Token、余额/额度和模型统计快照。两个连续成功快照之间，以累计实际扣费增量作为上游结算成本；余额减少额和额度已用增量作为第二、第三证据。首次采集只建立基线，不追认基线之前的成本。

核对同时比较同一账号在本地的请求数、Token 和本地监测成本：

- 累计计数回退时标记为上游重置或日志清理，该窗口不视为已核验。
- 上游请求/Token 明显高于本地时标记“API Key 可能被其他系统共用”；成本仍按较高值计入，避免高估利润。
- 上游请求/Token 明显低于本地时标记“上游数据延迟或少报”，使用本地保守成本并等待下一次采集复核。
- 上游返回的币种不是 USD、响应缺字段或时间不连续时，窗口保持未核验。

“明显差异”采用固定容差，避免网络边界造成误报：请求数差异超过 `max(2, 本地请求数的 1%)`，或 Token 差异超过 `max(1000, 本地 Token 的 2%)`。成本差异警告阈值为绝对差额超过 `$0.01` 且相对差异超过 `2%`。

上游余额差额、账单或用量明细属于时间窗口证据，保存在独立 reconciliation 记录中，不反向改写单请求日志。上游仅返回 `/v1/sub2api/billing` 价格倍率不属于结算证据。

### 保守利润

对同一账号和时间窗口，如果同时存在本地监测成本和结算成本，监测口径使用两者较高值：

```text
监测成本 = max(Σ 请求本地监测成本, 上游累计扣费增量, 可验证余额减少额)
毛利润 = 用户实际扣费 - 监测成本
毛利率 = 毛利润 / 用户实际扣费 * 100%，销售额为 0 时返回 null
```

如果只有上游声明价，页面并排展示声明成本，但监测成本仍使用本地审核/估算成本，并显示“未核验”。差异率使用 `abs(结算成本 - 本地成本) / max(本地成本, 0.000001)`，同时提供绝对差额，避免小额请求因百分比放大造成误判。

### 历史兼容

已有 `usage_logs` 记录没有利润监测快照。默认采用 `max(已记录账号成本, 倍率前基础成本)` 作为保守历史成本并显示“历史来源未知”，避免历史上游低报倍率继续抬高利润。不能用当前账号倍率回填历史记录。

## 后端设计

### 数据模型

- `accounts` 增加 `profit_cost_floor_multiplier`，默认 1.0，仅管理员可修改，且不受上游倍率同步影响。
- `usage_logs` 增加 `profit_monitor_cost`、`profit_base_cost_source`、`profit_rate_source`、`profit_cost_version` 四个可空字段；写入时冻结本地保守成本和来源。
- 新增 `upstream_cost_snapshots` 表，保存账号、采集时间、累计实际扣费、累计请求数、累计 Token、余额/额度、模型统计、响应版本和状态；不保存 API Key 或原始敏感响应。
- 新增 `upstream_cost_reconciliations` 表，按 `account_id + window_start + window_end` 唯一，保存本地成本、上游声明成本、累计扣费增量、余额减少额、最终结算成本、证据类型、差额、差异率、状态和采集时间。
- 基础成本来源值固定为 `custom_rule`、`channel_pricing`、`model_catalog`、`legacy_formula`、`unknown`；倍率来源值固定为 `approved_floor`、`upstream_probe_higher`、`unknown`。结算证据状态只保存在 reconciliation 表。
- 迁移和写入逻辑保持分区表兼容，历史数据只读不改写。

### 服务与查询

新增 `ProfitMonitorService`，负责：

- 将日期和时区转换为 UTC 半开区间 `[start, end)`。
- 聚合销售额、监测成本、利润、毛利率、请求数和 Token 数。
- 按 group/model/account 返回明细，保留零销售额和负利润行，便于定位亏损。
- 合并成本来源计数和 reconciliation 状态。
- 对有 reconciliation 的账号先按账号聚合，再取本地成本与结算成本的较高值，避免把一个窗口的账单重复叠加到每条请求。
- 将账号窗口的结算差额按该窗口内各请求的本地监测成本比例分配到分组、模型和日期；本地成本总和为零时保留为“未分配结算成本”，不按 Token 武断分摊。

新增 `UpstreamCostReconciliationService`，复用现有上游探测的超时、代理、并发上限和单实例任务锁，负责采集 `/v1/usage` 快照、计算连续快照差分、识别计数回退/共享 Key/数据延迟，并写入 reconciliation。网络采集不发生在利润页面请求链路中，页面只读取已落库结果。

新增管理员接口：

```text
GET /api/v1/admin/profit-monitor
```

参数：`start_date`、`end_date`、`timezone`、`group_id`、`model`、`account_id`、`page`、`page_size`。

响应包含：

- `summary`: sales, cost, profit, margin_percent, requests, tokens, unknown_cost_count, unverified_cost_count。
- `trend`: date, sales, cost, profit, margin_percent。
- `groups`, `models`, `accounts`: 相同指标加维度标识和来源状态。
- `reconciliations`: 上游结算核对结果、最新采集时间、差异和可信状态。

接口只读，查询失败时返回明确错误；单个来源缺失不吞掉整页，而是在响应中标记不完整统计。

## 前端设计

- 新增管理员路由 `/admin/profit-monitor` 和侧边栏“利润监测”。
- 顶部提供日期范围、分组、模型、账号筛选；默认最近 7 天。
- 顶部显示上游核对数据的最新采集时间，并提供只读刷新按钮；刷新只启动受限后台采集，不在浏览器中接触上游 API Key。
- 第一行展示销售额、监测成本、毛利润、毛利率；负利润使用红色，未知/未核验成本显示警告标记。
- 趋势图展示销售额、成本、利润三条线。
- 下方使用 Tab 展示“分组”“模型”“上游账号”表格，列出请求数、销售额、成本、利润、毛利率、成本来源和核对状态。
- 账号编辑页增加“利润监测审核成本倍率下限”；默认 1.0，并解释只有管理员确认合同折扣后才应降低。
- 页面文案明确“用量毛利（非现金利润）”，不把充值订单金额混入销售额。
- 支持空数据、查询失败、部分成本未知、销售额为零和移动端窄屏状态。

## 测试与验证

- Go 单元测试：成本来源优先级、保守 `max` 规则、累计扣费差分、余额差分、首次基线、计数回退、共享 Key、数据延迟、零销售额毛利率、负利润、历史未知来源和 UTC 半开区间。
- Go 仓储测试：快照幂等、按分组/模型/账号聚合、结算差额分配、筛选组合、reconciliation 唯一约束和分区写入。
- HTTP 适配器测试：`/v1/usage` 鉴权、代理、超时、响应大小、缺失字段、非 USD、异常状态码和敏感字段不落库。
- API 合约测试：管理员权限、参数校验、响应字段和部分数据缺失行为。
- Vue 测试：四张摘要卡、来源标记、负利润样式、Tab 切换、筛选参数和空/错误状态。
- 验证命令：`go test ./...`（按仓库 build tag 约定补充 unit/integration）以及前端 `pnpm test:unit`、`pnpm build`。

## 发布与回滚

先执行新增迁移，再部署后端；旧客户端不调用新接口，不影响现有计费。若监测接口异常，只回滚页面/API 路由和迁移后的新表，不回滚已有 `usage_logs` 成本字段和请求结算逻辑。
