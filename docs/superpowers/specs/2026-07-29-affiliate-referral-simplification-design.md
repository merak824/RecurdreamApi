# 邀请返利简化与专属用户提现设计

## 状态

设计已于 2026-07-29 在对话中确认，等待书面复核。

## 背景

现有邀请返利模块已经具备邀请码、邀请绑定、充值返利、余额转入、代理提现和后台记录等能力，但普通用户与 `agent` 代理使用两套返利余额和两套结算逻辑。代理角色无法通过现有用户管理接口正常设置，提现审核及代理用量接口也未完整接入路由，角色变化还可能使历史返利余额不可见。

本次调整保留现有邀请返利核心能力，将代理身份改为“专属用户配置中的提现权限”，并删除无关的代理等级和高级返利规则。实现应尽量复用现有服务、流水、提现页面和审核代码。

## 目标

- 所有用户都可以邀请新用户，并默认使用全局返利比例。
- 管理员可以为指定用户配置必填的专属返利比例、可选的专属邀请码和提现权限。
- 所有返利进入同一个余额池，所有用户都能将返利转入站内余额。
- 只有开启提现权限的专属用户可以申请微信或支付宝提现。
- 仅成功支付的余额充值和付费订阅产生返利，并以实际支付金额为基数。
- 接通完整的提现申请、后台审核、支付确认和驳回退回流程。
- 删除 `agent` 角色在邀请返利中的业务含义，以及代理等级、用量建议、独立余额池等无关逻辑。
- 保持旧数据库可平滑升级，避免直接删除历史字段导致部署风险。

## 非目标

- 不做多级分佣，只支持一级邀请关系。
- 不接入微信商户转账或支付宝自动转账 API，管理员线下人工打款。
- 不保存用户长期收款资料，每次提现单独选择渠道并上传收款码。
- 不处理返利退款冲正。平台业务规则不允许退款。
- 不对兑换码、赠送余额或管理员手工充值发放返利。
- 不保留冻结期、返利有效期、单个被邀请人返利上限或管理员充值返利规则。
- 不立即删除旧代理数据库字段和历史迁移文件。

## 用户与专属配置

### 普通用户

每个用户注册后都有唯一的系统邀请码。普通用户可以分享邀请链接，获得按全局比例计算的返利，并将可用返利转入站内余额。

### 专属用户

专属用户不是独立角色。管理员在系统设置的“专属用户配置”中添加用户后，为其配置：

- `aff_rebate_rate_percent`：专属返利比例，必填，范围为 `0-100%`。
- `aff_code`：专属邀请码，可选；未设置时继续使用系统生成的邀请码。
- `withdrawal_enabled`：是否允许微信提现或支付宝提现，默认关闭。

专属用户以“存在专属返利比例”为判定依据。`withdrawal_enabled=true` 只允许出现在有效专属配置上。删除专属配置时，系统必须清除专属比例、恢复系统随机邀请码并关闭提现权限。

专属配置只覆盖该用户作为邀请人时的返利比例和结算权限，不改变其登录权限、API 权限或其他用户角色。

## 邀请关系

- 邀请链接保持为 `/register?aff=<code>`。
- 新用户注册时使用链接或注册流程携带的邀请码绑定邀请人。
- 一个用户最多绑定一个邀请人，绑定成功后不可更换。
- 用户不能邀请自己。
- 无效邀请码不阻止注册，只跳过邀请绑定并记录日志。
- 关闭邀请返利总开关后，不建立新的邀请关系。

## 返利计算

### 返利来源

只有以下成功支付订单产生返利：

- 余额充值订单。
- 付费订阅订单。

余额兑换码、管理员手工增加余额、注册赠送和其他非支付额度不产生返利。

### 计算规则

返利基数使用订单实际支付金额 `pay_amount`，不使用订单标价 `amount`：

```text
返利金额 = 实际支付金额 * 有效返利比例 / 100
```

有效比例按以下顺序解析：

1. 邀请人存在专属配置时，使用专属返利比例。
2. 否则使用全局返利比例。

返利金额沿用现有金额精度规则。每个支付订单只能产生一次返利，继续使用订单审计记录和数据库事务保证幂等。

### 总开关

关闭总开关后停止新的邀请绑定和返利发放，但已有返利余额仍允许转入站内余额，已提交的提现仍允许管理员完成或驳回，避免资金被锁定。

## 统一返利余额

返利只使用现有普通余额字段：

- `aff_quota`：当前可用返利。
- `aff_history_quota`：累计历史返利。

不再根据用户角色或邀请绑定时的角色选择返利模式。新返利全部进入 `aff_quota`，返利转入站内余额和现金提现也都从 `aff_quota` 扣除。

返利转入站内余额允许用户输入任意大于 `0` 且不超过可用返利的金额，不再限制为固定金额档位。转入操作继续写入返利流水，并在同一事务内更新返利余额和用户站内余额。

## 提现流程

### 权限

只有同时满足以下条件的用户才能申请现金提现：

- 存在有效专属返利比例。
- `withdrawal_enabled=true`。

后端必须强制校验权限，不能只依赖前端隐藏按钮。没有提现权限的用户仍可正常转入站内余额。

### 用户申请

用户每次申请时提供：

- 提现金额：任意金额，最低 `1` 元，不得超过可用返利。
- 收款渠道：`wechat` 或 `alipay`。
- 当次收款码：PNG、JPEG 或 WebP，最大 2MB。

提交成功后，系统在数据库事务中立即从 `aff_quota` 扣留提现金额并创建 `pending` 申请，防止同一笔返利同时转余额或重复提现。

### 管理员处理

管理员在“邀请返利 > 提现审核”中查看用户、金额、渠道、收款码和申请时间。

- 标记已支付：可上传付款凭证并填写备注，状态变为 `paid`。
- 驳回：必须填写驳回原因，状态变为 `rejected`，金额在同一事务内退回 `aff_quota`。

只有 `pending` 申请可以处理。重复支付、重复驳回或支付后驳回返回冲突错误。删除专属配置不影响已经提交的申请，管理员仍可完成或驳回。

## 系统设置界面

邀请返利功能卡只保留：

- 邀请返利总开关。
- 全局返利比例。
- 专属用户配置表。

删除冻结期、返利有效期、单人返利上限和管理员充值参与返利等控件。

专属用户表显示：

- 邮箱。
- 用户名。
- 邀请码。
- 专属返利比例。
- 提现权限状态。
- 编辑和删除操作。

新增或编辑专属用户时，专属返利比例必填，专属邀请码可选，提现权限默认关闭。

## 用户界面

“邀请返利”页面统一展示：

- 当前有效返利比例。
- 邀请人数。
- 可用返利。
- 历史返利。
- 邀请码和邀请链接。
- 被邀请用户及其累计贡献返利。
- 转入站内余额。

删除普通用户/代理身份标签、代理模式提示和两套余额展示。只有拥有提现权限的专属用户显示提现入口和自己的提现记录。

提现弹窗允许用户输入金额、选择微信或支付宝并上传收款码。

## 后台管理

“邀请返利”后台菜单保留：

- 邀请关系。
- 返利记录。
- 转入余额记录。
- 提现审核。

删除代理 Token 用量、代理等级和建议返利比例相关接口与页面。后台记录支持现有的搜索、时间筛选、排序和分页能力。

## 接口调整

### 专属用户

专属用户读写模型增加：

```json
{
  "aff_code": "OPTIONAL_CODE",
  "aff_rebate_rate_percent": 20,
  "withdrawal_enabled": true
}
```

新增专属配置时比例必填。更新时允许修改三项。删除配置时恢复默认邀请码、清除专属比例并关闭提现权限。

### 用户返利详情

用户返利详情增加 `withdrawal_enabled`，删除当前模式、代理余额、代理历史余额和代理提现统计等角色相关字段。

### 提现申请

提现请求包含：

```json
{
  "amount": 10.5,
  "payment_method": "wechat",
  "collection_qr_data": "data:image/png;base64,..."
}
```

后台接入已有的提现列表、标记已支付和驳回接口，并将这些接口注册到管理员路由。

## 数据库兼容

新增 `user_affiliates.withdrawal_enabled BOOLEAN NOT NULL DEFAULT FALSE`。

升级迁移执行以下兼容处理：

1. 将旧 `agent_aff_quota` 合并到 `aff_quota`。
2. 将旧 `agent_aff_history_quota` 合并到 `aff_history_quota`。
3. 将旧 `agent_aff_frozen_quota` 合并到 `aff_quota`，因为新设计不再冻结返利。
4. 将旧 `aff_frozen_quota` 合并到 `aff_quota`。
5. 将旧 `agent` 用户改为普通 `user`。
6. 为旧 `agent` 用户保留现有专属比例；没有专属比例时，将迁移时的有效全局比例写为专属比例快照，并开启提现权限。
7. 清空旧代理余额字段，避免重复计算。

旧 `rebate_mode`、代理余额字段、冻结字段、提现表和旧设置键暂时保留，以兼容已经执行过的历史迁移和未来上游合并，但新代码不再读写无关字段。历史提现表继续用于新的专属用户提现流程，并增加 `payment_method` 字段。

## 错误处理与并发安全

- 邀请码必须唯一，冲突返回明确错误。
- 专属比例必须是有限数字且处于 `0-100%`。
- 转入金额必须大于 `0` 且不超过可用返利。
- 提现金额必须不少于 `1` 元且不超过可用返利。
- 提现渠道只允许微信或支付宝。
- 收款码必须是允许的图片类型且不超过 2MB。
- 转余额、提交提现、支付确认和驳回都使用数据库事务。
- 扣减返利前锁定对应用户返利行，防止并发超额支出。
- 管理员只允许处理 `pending` 提现申请。
- 缓存失效沿用现有余额与鉴权缓存处理。

## 测试策略

### 后端

- 普通用户使用全局比例，专属用户优先使用专属比例。
- 专属比例为 `0%` 时不产生返利，但仍是有效专属配置。
- 余额充值和付费订阅按 `pay_amount` 返利。
- 兑换码和管理员手工充值不返利。
- 同一支付订单不会重复返利。
- 任意合法金额可以转入站内余额，超额和非正数被拒绝。
- 非专属用户、未开启提现的专属用户不能提现。
- 提现金额低于1元、超额、非法渠道和非法图片被拒绝。
- 提现提交扣减返利，支付确认完成申请，驳回退回返利。
- 重复处理提现和并发超额提现被拒绝。
- 删除专属配置后，未处理提现仍可完成或驳回。
- 旧代理余额、冻结余额和角色迁移正确且不会重复合并。

### 前端

- 系统设置只显示总开关、全局比例和专属用户配置。
- 新增专属用户时比例必填，提现权限默认关闭。
- 专属用户列表正确展示提现权限。
- 用户返利页不再显示代理身份和双余额。
- 所有用户可以输入任意合法金额转余额。
- 只有有权限的专属用户看到提现入口。
- 提现弹窗支持微信/支付宝、最低1元和收款码校验。
- 后台提现审核页支持查看、支付和驳回。

### 完整验证

- 后端完整 Go 测试。
- 前端单元测试。
- TypeScript 类型检查。
- ESLint。
- 前端生产构建。
- 数据库迁移在空数据库和包含旧代理数据的数据库上验证。

## 上线与回滚

部署时先执行数据库迁移，再同时发布后端和前端。总开关保持关闭，管理员完成全局比例和专属用户配置后再开启。

上线前至少验证一次完整流程：邀请注册、成功充值、返利到账、转入余额、专属用户提交微信提现或支付宝提现、管理员支付确认和驳回退回。

回滚代码时旧字段仍然存在，但兼容迁移已经将代理及冻结余额合并到普通返利余额。回滚版本不得再次自动合并这些余额；迁移必须记录一次性执行状态并保持幂等。
