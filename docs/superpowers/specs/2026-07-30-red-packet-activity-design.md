# 红包活动设计

## 目标

在 `recurdream-api` 现有 Vue 工作台中增加平台官方红包活动。普通用户可以查看当前活动、参与并查看开奖记录；管理员可以在独立管理路由创建和管理活动。奖励使用站内余额单位直接入账，不改变用户充值统计，也不扣除管理员余额。

## 已确认规则

- 只有管理员可以创建官方红包，普通用户不能发红包。
- 红包类型包括拼手气红包和固定红包。
- 管理员分别设置目标参与人数、中奖人数和红包总额，中奖人数不得超过目标参与人数。
- 活动发布后持续有效，达到目标参与人数后自动封盘并开奖。
- 同一用户在同一活动中只能参与一次。
- 参与资格为二选一：历史净成功充值不少于 1 元，或可用邀请抽奖积分不少于 2 分。
- 每成功邀请 1 人注册，邀请人获得 1 个邀请抽奖积分。邀请注册成功只发放一次积分。
- 同时满足充值和积分条件时优先使用充值资格，不消耗积分。
- 未达到充值条件时，参与操作原子消耗 2 个邀请抽奖积分；积分不足时不能参与。
- 重复参与、活动已满、活动已进入开奖或参与事务失败时不消耗积分。
- 兑换码奖励、管理员余额调整不计入充值资格；退款会减少净充值资格。
- 参与成功后，即使用户后续退款导致不再满足充值资格，也不从当前活动移除。
- 资格阈值和积分消耗规则在活动发布时快照，后续系统设置调整只影响新活动。
- 拼手气红包从中奖人数中随机抽取中奖者并随机分配金额，每位中奖者至少获得 0.01。
- 固定红包从中奖人数中随机抽取中奖者，并将总额按分为单位平均分配；总额必须能被中奖人数整除。
- 活动奖励是平台营销奖励，不扣管理员余额、不增加充值总额，写入独立红包奖励流水。
- 全局同时只能存在一个 `active` 或 `drawing` 活动；草稿和历史活动不限。
- 活动状态为 `draft -> active -> drawing -> completed`，`active -> canceled` 允许，`drawing` 不可取消。
- 正常状态账户均可参与，包括管理员账户；禁用、封禁和已删除账户不能参与。

## 用户端设计

用户端沿用现有 `AppLayout` 工作台：左侧导航、顶部栏、浅灰页面背景、青绿色主色、白色数据卡、现有按钮和表单尺寸。红包的红色和金色只作为奖励金额、红包图标和“手气最佳”状态的语义强调，不使用整页大红色封面。

用户侧导航只显示“红包活动”，不显示管理员入口。页面包含两个用户可见视图：

1. 当前活动：活动名称、状态、活动编号、红包总额、中奖人数、目标参与人数、参与进度、自动开奖提示、最近参与用户和活动规则。
2. 开奖记录：脱敏中奖用户名、奖励金额、到账状态、到账时间、我的奖励和奖励流水号。

参与前显示当前/目标参与人数以及最近参与用户。开奖后所有已登录用户均可查看中奖名单和金额；用户名采用首字符和末字符保留、中间替换为 `***` 的规则，长度不足 3 个字符时仅保留首字符。拼手气红包金额最高者标记“手气最佳”；并列时按中奖结果写入顺序取第一位。

资格卡必须明确呈现“满足任一项即可”，用“或”分隔两条资格：

- 累计净充值：显示当前值、阈值和满足状态。
- 邀请抽奖积分：显示可用积分、参与所需积分和每次成功邀请的积分来源。

当用户同时满足两项时，参与按钮附近显示“本次使用：充值资格”和“不消耗邀请积分”。当用户只能使用积分时，显示“本次消耗 2 个邀请积分，参与后剩余 N 个”。参与成功后立即更新按钮、进度和积分余额，并通过 toast 确认实际采用的资格路径。

## 管理端设计

管理端复用现有后台工作台和管理员导航，只在管理员菜单中展示红包活动。普通用户看不到管理菜单，直接访问管理员路径时由现有 `requiresAdmin` 路由守卫重定向到用户仪表盘；后端接口同时要求管理员权限。

管理页面包含：

- 当前活动摘要：活动编号、类型、金额、参与进度、中奖人数、状态和取消操作。
- 创建活动表单：名称、红包类型、总额、目标参与人数、中奖人数、祝福语。
- 资格快照预览：净充值阈值、积分阈值、充值优先、积分消耗规则和“发布后锁定”说明。
- 历史活动表：活动编号、类型、总额、参与/中奖人数、状态和创建时间。

已有活动进行中时，创建表单可以保存草稿，但发布按钮禁用并提示“当前活动结束后可发布”。发布参数不可修改；需要调整时复制为新草稿。

## 后端状态与事务

参与接口在一个数据库事务中完成：

1. 锁定活动并确认状态为 `active`、目标人数未达到、用户未参与且账户可参与。
2. 优先检查快照后的净充值资格；不满足时检查可用邀请积分并原子扣减 2 分。
3. 写入唯一参与记录并增加参与人数。
4. 最后一位符合条件的参与者将活动从 `active` 改为 `drawing`，同时使用操作系统密码学安全随机源生成并持久化 32 字节开奖种子。

开奖 worker 扫描 `drawing` 活动。它以活动编号、开奖种子和不同用途标签派生确定性随机字节流，使用拒绝采样避免取模偏差，并通过 Fisher-Yates 洗牌抽取中奖者。所有金额都转换为整数“分”计算：固定红包要求总分数能被中奖人数整除；拼手气从 `1..总分数-1` 中无偏抽取 `中奖人数-1` 个不同切点，排序后用相邻切点差生成每份金额，再按独立派生的随机顺序分配给中奖者。该算法保证每份至少 1 分且分配总和与红包总额完全一致；红包总分数小于中奖人数时禁止发布。

中奖记录、余额变更、红包奖励流水和 `completed` 状态在同一事务内提交。数据库唯一约束防止重复参与、重复中奖和重复入账。worker 重启后继续处理 `drawing` 活动；余额缓存刷新失败不回滚已提交流水，并进入可恢复刷新队列。

邀请积分应使用独立的积分账户/流水，而不是直接依赖累计邀请人数：成功注册事件幂等增加 1 分；参与积分资格路径幂等扣减 2 分；流水记录活动编号、用户编号和来源事件，便于审计和恢复。

## API 与数据边界

用户端需要：当前活动、活动详情、参与资格、参与操作、开奖记录和我的奖励流水接口。管理员端需要：草稿创建、草稿更新、发布、当前活动摘要、取消、活动历史和导出接口。所有参与与积分接口必须以服务端状态为准，前端显示仅用于反馈。

实体为：`red_packet_activities`、`red_packet_participants`、`red_packet_winners`、`red_packet_reward_ledger`、`invite_lottery_point_ledger`。活动表保存发布时资格快照、整数分金额、随机种子和状态时间；积分流水保存增减方向、数量、来源邀请记录或活动参与记录。

数据库约束包括：

- `red_packet_activities` 上针对 `active`、`drawing` 状态的全局部分唯一索引。
- `red_packet_participants(activity_id, user_id)` 唯一约束。
- `red_packet_winners(activity_id, user_id)` 唯一约束。
- 奖励流水以活动和中奖记录组成唯一业务键，邀请积分发放以邀请注册记录组成唯一业务键，积分消耗以活动和参与记录组成唯一业务键。
- 金额、参与人数、中奖人数、状态迁移和积分余额使用数据库检查约束及事务内条件更新共同保护。

## 错误与恢复

- 资格不足：分别说明还差多少净充值或多少积分，不使用模糊的“不可参与”。
- 积分并发扣减失败：返回可重试提示，不能出现扣分但未写入参与记录。
- 活动已满或已开奖：按钮变为不可用，用户可转到开奖记录。
- 固定红包金额不能整除：在管理员表单中就地提示，不允许发布。
- 中奖事务失败：整体回滚，活动保持 `drawing`，worker 后续自动恢复。
- 管理员误取消：取消前二次确认；`drawing` 状态不显示可取消按钮。

## 测试策略

- 领域测试：充值优先、积分不足、积分原子扣减、邀请注册幂等加分、重复参与、固定金额整除、拼手气最小 0.01。
- 并发测试：最后一个参与者只触发一次 `drawing`，重复请求不重复扣积分或入账。
- worker 测试：开奖重试、事务回滚、重启恢复和重复 worker 安全性。
- API 权限测试：普通用户无法访问管理员接口和页面；管理员能访问；活动进行中不能修改已发布参数。
- 前端测试：用户端资格二选一展示、充值优先提示、积分参与后的余额更新、用户端不渲染管理员入口、管理员表单校验。
- 浏览器回归：375px、768px、1440px，检查无横向溢出、44px 触控尺寸、键盘焦点、减少动态效果和深色模式对比度。
